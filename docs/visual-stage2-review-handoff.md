## 검토 질문

2단계 테스트에서는 근거 텍스트가 그림을 설명하는 글이었다. 그런데 실제로는 그림 속 글자와 그림 자체가 입력되고, 그 글자가 다시 그린 그림에 그대로 들어간다. 이 경우 2단계 테스트와 다르게 흘러가지 않는가?

## 결론

- 그림 오생성 차단은 실제 경로에서도 유지된다. 다만 모든 visuals를 내용과 무관하게 보류하기 때문이다(`lib/summary.js` `heldVisuals++`). `suppression-check`의 0 mismatch는 판별력이 아니라 전부 보류한 결과다. 정상 그림을 살리는 능력은 측정된 적이 없다.
- 수식과 본문은 테스트와 다르게 흘러간다. 아래 1, 4번은 3단계 전에 고칠 2단계 회귀다.

## 발견 사항

1. **근거 모양이 다르다.** 제품에서는 PP-OCR 줄이 `layoutText`를 거쳐 `EvidenceStore.add`로 들어가고, 이때 `\s+`가 공백 하나로 합쳐진다(`lib/evidence.js:3,7`). 그래서 화면 한 장이 근거 한 줄이 된다. 테스트는 이 단계를 건너뛰고 `x=2`, `x=\n2` 같은 단독 근거를 바로 넣었다.
   - 실제 코퍼스를 제품 경로로 돌리면 수식 복원은 0/6이다. 허용 대조군은 화면에 수식 한 줄만 있을 때만 생긴다.
   - 반대로 여러 줄 수식 보류 보장은 실제로 깨진다. `y =` 다음 줄에 `mx + b`가 오면 `y = mx + b`로 합쳐져 허용된다. `visual-suppression-check.mjs`의 `multiline-equation` 사례와 `summary.test.js`의 "raw OCR before whitespace normalization" 테스트는 정규화를 건너뛰어서만 통과한다.
2. **그림 속 글자를 그대로 옮기면 OCR 오독이 "근거 있음"으로 통과한다.** 기준이 "출력 = OCR 문자열"이기 때문이다.
   - 재현 결과, 세로 분수 x=½를 `x = 12`로 읽거나 마이너스가 빠진 `x = 2`를 그대로 옮기면 허용된다.
   - 코퍼스에서 실제로 나온 오독은 다음과 같다: `ax2`(ax²), `√62-4ac`(b²), `Y1`/`Y2`(y₁/y₂), `*1`(x₁), `γ`(y), `중`(세로 축 라벨, 신뢰도 0.09).
   - 이제 본문에서 수식 표기를 금지하므로 이런 오독이 본문에 그대로 실릴 수 있다. 본문에는 수치 검사가 없다.
   - 4단계에서 라벨 텍스트 대조는 항상 통과한다. 연결·부호·첨자·축 대응은 원본 이미지와 직접 비교해야만 검증된다.
3. **비전(클라우드) 엔진에서는 그림 설명문이 실제로 근거가 된다.** `server/index.js:14` `VISION_PROMPT`가 수식은 `$...$`, 표는 마크다운 표, 그래프는 한두 문장 설명으로 적게 한다. 이 경로는 2단계 테스트에 한 건도 없다.
   - 수식은 전부 보류되므로 안전하다.
   - 설명문이 틀려도 본문에 그대로 들어간다.
   - 근거의 `$..$`를 인용한 항목은 탈락한다. 핵심 결론이 전부 탈락하면 청크 요약 자체가 실패한다.
4. **`richStructure`가 정상 문장을 오탐한다(회귀).**
   - 제목이 `Graph theory 3강`이면 요약 전체가 실패한다(`lib/summary.js:155`의 throw).
   - `|x| < 1 이면 수렴`, `Pie chart는 …`, `Graph theory의 정의`, `가격은 $5에서 $10로`가 들어간 항목은 탈락한다. 결론이 그것 하나뿐이면 요약이 실패한다.
   - 2단계 이전 프롬프트는 본문에 `$...$`를 강제했다. 그래서 기존 보관 노트를 열면(`offscreen.js:30`) 수식이 있는 항목이 모두 빠지고, 결론이 전부 수식이면 노트가 열리지 않는다. 저장소의 `lecture_summaries/*`에도 수식 줄이 수십에서 수백 개 있다.

## 2단계 재검토 — 실제 강의 화면 3장 (2026-10-04)

사용자가 MOSFET 강의 화면 3장을 제공했다. 1장은 수식 위주, 2장은 그래프, 3장은 소자 단면 그림이고, 세 장 모두 빨간 손글씨가 덧칠되어 있다. 이 이미지와 OCR 원문은 강의 자료라서 커밋하지 않았다.

### 제품 경로 재현

`tools/visual-ocr-replay.mjs`는 `session.js`와 같은 순서로 처리한다: 캔버스 → JPEG(q .9) → `PpOcrV5` → `layoutText` → `EvidenceStore`. 클라우드 컨테이너의 CPU에서 측정한 처리 시간은 장당 1.5~3.8초다. 비전(클라우드) 경로는 서비스 토큰이 없어 실행하지 못했다.

- **세 장 모두 좌표가 붙었다.** 수식 줄이 조각나 흩어진 배치로 판정되기 때문이다. 이전 프롬프트(2e972b2)였다면 그림이 없는 1장까지 도식으로 다시 그렸을 것이다. 좌표가 있다는 것은 그림이 있다는 뜻이 아니다.
- **OCR 결과만으로는 일반 텍스트, 수식, 그림 라벨, 손글씨를 구분할 수 없다.** 넷이 한 근거 줄에 섞이고, 표시도 신뢰도 차이도 없다(손글씨 0.29~0.66, 인쇄 수식 조각 0.46~0.83).
- **수식:** 아래첨자가 소실되고(`VGs`, `VrHl`, `Vps`), 분수가 줄 단위로 갈라지고(`1`, `W`, `L`), ½는 `∂`나 `Z`로 읽혔다.
- **손글씨:** `Current`가 `CUNON`이 되고, V_DS=V_GS−V_TH는 `VDs=VGs-VM`, V_DS>0은 `UbS70`이 됐다.
- **3장 핵심 문장 소실:** "Channel pinches off when V_DS > V_GS − V_TH"가 손글씨에 덮여 `Chan inahsffhe > w`가 됐다.
- **그림 라벨 대부분 누락:** 3장의 n⁺, V_G, V_D, L₁, L, E 같은 라벨이 거의 읽히지 않았다. 그래프 곡선과 단면 형상은 텍스트로 전혀 오지 않는다.

### 일반 텍스트와 그림 구분 시제품

`tools/visual-region-probe.mjs`는 새 모델 없이 픽셀과 OCR 상자만으로 영역을 나눈다.

- **손글씨 층:** 채도 높은 빨간 잉크.
- **그림 후보:** OCR 상자 밖의 검은 인쇄 잉크 조각을 40px 안에서 묶고, 질량이 60셀 이상인 것만 남긴다.

결과:

- 화면 단위 그림 영역은 정답과 같았다. 1장은 0개(수식의 적분·분수선은 OCR 상자에 흡수됨), 2장은 그래프 1개, 3장은 단면 그림 2개였다. 펜 커서는 걸러졌다.
- OCR 줄 분류는 57개 중 52개가 맞았다. 손글씨 10/10, 그림 라벨 10/14, 일반 텍스트 32/33이었다.
- 틀린 5건은 그래프 왼쪽 y축 라벨 4건과, 그림 바로 위의 본문 1줄이다.

한계도 분명하다.

- 임계값을 바로 이 3장에서 정했으므로 일반화 성능이 아니다.
- 빨간색이 아닌 손글씨, 특히 검은 펜은 색으로 구분할 수 없다.
- 영역을 찾아도 OCR 라벨만으로는 그림을 다시 그릴 수 없다. 단면 형상과 곡선은 텍스트가 아니기 때문이다.

### 3단계 설계에 반영할 점

1. 근거를 한 줄로 합치기 전에 OCR 줄마다 영역 등급(text, figure, hand)을 붙인다. 요약 입력에는 일반 텍스트만 본문 근거로 넣고, 손글씨는 "판서"로 따로 표시한다.
2. 그림 재구성의 입력은 OCR 라벨이 아니라 영역 이미지(crop)여야 한다. 로컬 후보(Chrome 내장 AI, Qwen-VL 등)는 crop 단위로 비교한다.
3. 손글씨는 텍스트 복원률이 낮다. 짧은 수식 판서는 crop 인식 후보로 두고, 스케치 판서(S–D 채널 그림)는 재구성이 아니라 "판서 있음 · 위치" 표시나 원본 crop 표시로 처리할지 결정이 필요하다. crop을 보관하면 이미지 저장 금지 불변식과 충돌하므로 사용자 결정이 필요하다.
4. 평가셋에 다음을 추가한다: 검은 펜 판서, 수식만 있는 화면(음성 대조), 축 라벨이 그래프 밖에 있는 그래프.

### 재현

```
node tools/visual-ocr-replay.mjs 1.png 2.png 3.webp replay.json
node tools/visual-region-probe.mjs replay.json out/ truth.json   # 영역 오버레이 PNG + 분류 혼동표
```

Playwright가 전역에 설치되어 있으면 `PLAYWRIGHT_MODULE=<경로>`, 다른 브라우저를 쓰려면 `CHROME_PATH=<경로>`를 지정한다. 실제 강의 이미지·OCR 결과·truth 파일은 저장소 밖에 둔다.

## 시간축 판서 분리 시제품 (2026-10-04)

**사용자 제안.** 강의는 깨끗한 슬라이드가 먼저 나오고 그 위에 손판서가 시간에 따라 쌓인다. 지금은 화면이 바뀔 때마다 판서와 강의안을 통째로 다시 캡처한다. 판서가 시간에 따라 생긴다는 점을 쓰면 둘을 분리할 수 있다.

**방법.** `tools/visual-ink-layer-probe.mjs`를 썼다.

- 같은 슬라이드(`slideId`)의 첫 프레임을 기준 화면으로 둔다.
- 이후 프레임에서 기준 화면과 픽셀이 달라진 곳을 판서 층으로 본다. 4px 칸 단위로, 밝기나 색이 50 넘게 다른 픽셀이 2개 이상 있는 칸이다.
- "지속" 규칙은 연속 두 프레임에서 모두 달라진 칸만 판서로 인정한다.
- 판서 층 조각마다 판서 부분만 남긴 이미지를 OCR한다. 신뢰도 0.9 이상이고 무채색 검은 잉크가 70% 이상이면 "인쇄 추가(애니메이션)"로 분류한다.

**측정 조건.** 공개 코퍼스 3장 위에 합성 시퀀스를 만들었다.

- 프레임 순서: f0 깨끗한 화면 → 빨간 원 → 검은 낙서+밑줄 → 인쇄 글줄 등장 → 파란 화살표 → 펜 이동.
- 각 프레임에 영상 압축(JPEG 0.55)과 제품 캡처(JPEG 0.9)를 거쳤다.
- Haiku가 다시 실행해 시간 외 수치가 같음을 확인했다.

**결과.**

| 항목 | 지속 규칙 없음 | 지속 규칙 (연속 2프레임) |
|---|---|---|
| 마지막 프레임 정밀도 / 재현율 | .79 / .99 | **.91 / .99** |
| 판서에서 멀리 떨어진 오탐 칸 | 177 | **0** (남은 오차는 획 경계 1칸) |
| 움직이는 펜 커서 오탐 | 프레임당 약 57칸 | **0** |
| 멈춰 있는 펜 커서 오탐 | — | 슬라이드당 54~55칸 (**미해결**) |
| 새로 그은 획의 재현율 | .99 | 첫 프레임 .50~.75, 다음 프레임부터 .99~1.00 |

- 애니메이션으로 등장한 인쇄 글줄 9조각은 모두 "인쇄 추가"로 분류됐다. 판서를 인쇄로 잘못 분류한 것은 0건이다.
- 판서가 덮인 화면 전체를 OCR하면 인쇄 글자 유사도가 0.47로 떨어진다. 애니메이션 글줄을 뺀 대조 화면 기준으로도 0.74다. 예: `계수를`이 `생를`이 되고, `y = mx+b` 줄은 통째로 사라진다. 기준 화면을 한 번만 OCR하면 이 손상이 없다.
- 판서 층 계산(차이 비교와 조각 묶기)은 800×600 기준 프레임당 약 6ms다. OCR은 제외한 시간이다.

**남은 한계.**

1. 멈춰 있는 펜 커서는 지속 규칙을 통과한다. 모양·크기 판별이나, 조금 뒤 사라지는 칸을 되돌리는 규칙이 필요하다.
2. 지속 규칙은 한 프레임 늦다. 판서가 끝나고 화면이 멎은 뒤 두 번째 프레임을 기준으로 써야 한다.
3. 반듯하게 쓴 검은 손글씨 단어는 "인쇄 추가"로 잘못 분류될 수 있다(검증하지 않음). 색깔 있는 인쇄 애니메이션은 판서로 분류된다.
4. 검은 인쇄 글자 위의 검은 잉크는 차이가 생기지 않는다. 판서 픽셀의 6.5~8.6%가 여기에 해당한다. 칸 단위 재현율은 대체로 유지되지만 판서만 남긴 이미지에서는 획이 빠진다.
5. 첫 캡처에 이미 판서가 있거나 화면이 확대·스크롤되는 경우는 시험하지 않았다. 실제 강의 영상 구간으로 검증해야 한다.
6. 제품 경로 주의: `lib/visual-gate.js`는 256×144 표본에서 한 타일의 3.5% 이상이 바뀌어야 다시 캡처한다. "5V" 같은 짧은 판서는 캡처 자체가 안 될 수 있다.

**제품 통합 시 바뀌는 점(제안, 미구현).**

- 슬라이드별 기준 프레임 한 장을 offscreen 세션 메모리에만 둔다. 메모리 처리 원칙과 맞고, 슬라이드가 바뀌면 버린다.
- 인쇄 글자 OCR은 기준 화면에서 한 번만 한다.
- 판서는 판서만 남긴 조각을 OCR해, 등장 시각과 함께 별도 근거 종류("판서")로 넣는다. 그러면 음성과 시점 연결도 된다.
- 판서 텍스트 복원률은 여전히 낮을 것이므로, 스케치 판서의 표시 방식은 사용자 결정이 필요하다.

## 슬라이드 전환 판정 수정 (2026-10-05, `lib/visual-gate.js`)

**문제.** 기존 규칙은 64×36 화면에서 밝기 칸의 32% 이상이 바뀌면 새 슬라이드로 봤다. 그런데 실제 흰 배경 슬라이드 전환 7쌍은 모두 0.06~0.31이라 한 번도 전환으로 잡히지 않았다. 판서 추가는 0.03~0.04였다. 그 결과 다음 두 문제가 있었다.

- `slideId`가 늘지 않았다.
- 비전 모드는 전환일 때만 화면을 보내므로 첫 장 이후 거의 아무것도 보내지 않았다. 기존 테스트는 화면 전체 밝기를 바꾸는 가짜 프레임이라 이를 잡지 못했다.

**새 규칙 (사용자 지시).** 슬라이드의 첫 프레임을 기준 화면으로 둔다.

- 기준 화면의 내용 칸 중 20% 넘게 배경으로 돌아가면 새 슬라이드다. 이미 인식한 강의안과 달라졌다는 뜻이다.
- 판서를 더하거나 지우는 것은 기준 화면에 없던 칸의 변화라서 전환이 아니다.
- 기준 화면이 거의 비어 있으면(내용 칸 1% 미만) 반대로 내용이 1% 이상 나타났는지를 본다. 흰 로딩 화면 다음에 슬라이드가 나오는 경우를 위한 것이다.
- `reset()`(일시정지 후 재개, 에포크 변경)은 새 슬라이드로 시작한다.

**검증.**

- `node --test lib/*.test.js` 123개 통과. 새로 추가한 6개 테스트가 기존 규칙에서 놓치던 전환을 포함한다.
- 실제 화면 재생(판서 추가 → 지움 → 전환 → 판서 → 전환, 실제 강의 화면 3장, 흰 화면 → 슬라이드)에서 OCR·비전 두 모드 모두 기대한 `slideId`와 일치했다. 비전 모드는 판서에서 화면을 보내지 않고 전환에서만 보냈다.
- 기존 코드로 같은 재생을 돌리면 `slideId`가 계속 0이었고, 비전 모드는 첫 장 이후 0건이었다.

**남은 위험.**

- 기준 화면에 이미 판서가 있었는데 그 판서를 많이 지우면 전환으로 볼 수 있다.
- 사진이나 그라데이션 배경 슬라이드는 검증하지 않았다.
- 거의 빈 화면 위에 손판서를 시작하면 한 번 새 슬라이드로 잡힌다.
- 임계값은 10쌍으로 정한 값이라 실제 영상 검증이 필요하다.
