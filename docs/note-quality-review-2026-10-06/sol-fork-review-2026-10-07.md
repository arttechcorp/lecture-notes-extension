# sol-fork 실험 검토와 다음 설계

2026-10-07. 우선순위: **노트 품질 → 가격 → 소요 시간**. 분석 제안이며 이번 검토에서 런타임·배포·기본 모델은 변경하지 않았다.

## 결론

추천 후보는 **Sol 편집 계획 → Luna High 섹션 작성 → Sol 통합 검수·필요한 부분만 수정 → 코드 조판**이다. sol-fork 전체 Sol 작성은 품질 비교 기준으로 유지한다. 자유롭게 반복하는 에이전트나 매 작업마다 Sol→Luna→Sol을 거치는 현재 도구 경로를 기본으로 채택할 근거는 부족하다.

현재 실험은 고정 접두 캐시와 병렬 실행의 작동을 입증했다. 그러나 예시 PDF 수준의 구조화·시각화나 원문 대비 정확성의 우월성을 입증하지 않았다. 더 많은 Sol 호출보다 내용의 편집 설계와 그림·조판 경로를 먼저 개선해야 한다.

## 1. 확인한 실험 결과

auto debug 세션의 4군 보고와 실제 fork 진단의 마지막 실행을 대조했다. 아래 비용·캐시 수치는 auto debug의 호출 집계 보고값이며 이 검토에서 청구 원장을 재조회한 값은 아니다.

| 방식 | 보고 비용 | 생성 시간 | 자동 핵심 항목 커버리지 | 문항 블록 채움 |
|---|---:|---:|---:|---:|
| Sol 계획 + Luna High 독립 작성 | $0.142 | 약 4분 | 29/29 | 3/5 |
| Sol 누적 세션 | $0.368 | 3분 46초 | 13/28 | 0/5 |
| Sol 누적 세션 + Luna 도구 | $0.467 | 약 7분 | 13/24 | 0/4 |
| Sol 고정 계획 fork | $0.990 | 약 4분 36초 | 25/25 | 4/5 |

- 누적 세션 2군에는 과거 서버 본문 상한에 따른 413이 각각 33/31건 있었다. 현재 수정 후의 정상 동작이나 본질적 모델 품질 비교로 사용할 수 없다. 실패로 생성량도 달라져 완성 노트당 가격 비교 역시 부적절하다.
- fork 마지막 실행은 진단 기준 275.864초, 413·작성 timeout·섹션 탈락 이벤트 없음. 초안 입력은 약 44.1k–50.5k로 누적 증가하지 않았다. 보고상 쓰기 12호출에서 매번 cache read 27,275토큰이 관측됐다. 이는 공통 접두 재사용 증거이며, 계획 출력·추론까지 접두 전체가 캐시됐다는 증거는 아니다.
- fork는 baseline보다 약 7배 비쌌다. 출력·추론·복구·공통 입력 재처리를 함께 봐야 하며, cache hit 자체를 절감 성과로 삼으면 안 된다.
- fork의 자동 집계: 초안 주장 101, kept 83, relinked 2, collateral 16. 블록 탈락 3건(표 구조, 작성 거절, 의존 연쇄). 핵심 커버리지 100%와 내용 손실은 동시에 존재한다.
- 문항 4/5는 문항 블록 채움 지표이지 정답률이나 실제 문항 개수가 아니다. 각 군이 새 계획을 만들어 분모도 다르다. 동일 입력 1회 결과이므로 통계적 우열을 말할 수 없다.
- baseline의 E2E report는 진단 파일 다운로드 오류로 fail이다. 노트 생성 결과와 전체 테스트 성공은 구분해야 한다.

## 2. PDF에서 확인한 품질 병목

fork PDF는 21쪽. 1·3·9·10·19쪽을 메모리에서 렌더링해 확인했고, baseline 19쪽 중 3쪽도 대조했다. 전 페이지 사실 검증은 수행하지 않았다. 예시 교재의 목표는 기존 `source-analysis.md`의 IMFACT·LIMIT 전수 분석을 참고했다.

| 관찰 | 품질에 미치는 영향 | 우선 개선 |
|---|---|---|
| fork 1쪽 개념 연결이 링크와 단순 관계 행 위주 | 개념 지도처럼 보이지만 관계의 이유·조건이 잘 드러나지 않음 | 관계마다 유형·방향·설명·근거를 갖는 의미 구조를 설계 |
| 3쪽 개념 속성 설명과 아래 그래프 설명에 반복 | 페이지를 늘리지만 새로운 이해를 주지 못함 | 정의 / 비교 / 그림 해석의 설명 소유자를 구분 |

| 19쪽 도표 누락 표시와 큰 빈 공간 | 핵심 시각 자료가 최종 결과에 없을 수 있음 | 생성 전후 asset 연결·렌더 성공 추적, 누락 이유별 복구 |

마지막 진단의 figure 흐름은 `cropExist=25 → selected=21 → planAssigned=16 → textRef=6 → renderOk=4`다. 단계별 집계 단위와 적격 조건을 확인하기 전 이를 단순 누락률로 계산하지 않는다. 다만 모델 변경보다 먼저 조사할 구체적인 경로다. 이미지가 마지막에 나열되는 것과 설명에 통합된 시각화는 다르다.

예시 교재에서 가져올 핵심은 장식이 아니라 **개념 계층, 같은 축의 비교, 사례 단서와 해석의 대응, 조건·예외, 적용 문제와 근거**다. 모든 단원에 그림을 강제하지 않는다.

## 3. Luna는 어떻게 호출할 것인가

### 권장 기본: 코드가 실행하는 제한된 작성 워커

Sol이 편집 계획을 만들고 코드가 Luna High를 병렬 호출한다. 역할상 서브에이전트지만, 구현은 입력·출력이 고정된 모델 호출이다. 독립 세션에서 임의 도구를 반복 호출하는 에이전트 루프는 필요 없다.

각 작업 입력:

- 전체 학습 목표, 단원 구조, 공통 용어·표기, 섹션 간 설명 소유권.
- 해당 섹션의 근거와 조건·예외·정정, 필요한 선행 개념 요약.
- `visualIntent`: comparison / process / relation / graph-reading 등, 비교 축·관계·근거·asset ID. 원본 수치가 없으면 수치 그래프를 만들어내지 않는다.
- 설명 역할별 예상 출력량과 구조화된 SectionDraft 계약.

출력은 주장·근거·관계·시각화 명세이며 HTML/CSS가 아니다. 코드가 검증·조립하고, Sol 통합 편집자는 검증된 주장 요약과 미해결 문제를 보고 수정할 블록·관계만 반환한다. 판단에 필요한 근거는 함께 제공하거나 제한된 조회로 가져온다. 요약만 보고 사실을 확정하지 않는다.

### Sol이 직접 위임해야 한다면: 한 번의 배치 도구

`draft_sections({sectionIds, revision})`를 제공하고 서버가 미리 검증한 작업 목록에 매핑한다. 내부적으로 Luna를 제한된 동시성으로 실행한다. 반환은 작업 ID, 구조화된 핵심 결과, 검증 실패, 커버리지, 필요 시 조회할 산출물 ID다. 산출물은 실행 중 클라이언트 메모리에 두고, 재개용 파생 저장은 기존 암호화 저장소만 사용한다.

서브에이전트와 도구는 양자택일이 아니다. **도구가 Luna 워커를 실행하는 인터페이스**가 될 수 있다. Sol이 섹션마다 허가하고 전체 본문을 다시 생성하도록 하지 않는다. 기본 1회 배치 + 통합 검수 1회, 이후 미해결 고위험 항목만 제한된 복구 대상으로 둔다.

현재 `sol-luna-tool`은 각 작성 단계에서 도구 호출을 강제하고, Luna에는 서버의 기존 작업을 전달한 뒤 Sol이 최종 결과를 생성한다. Sol의 자유로운 작업 설계가 Luna에 전달되는 구조가 아니므로, 도구를 붙였다는 사실만으로 계획–작성 협업이 좋아졌다고 할 수 없다.

## 4. Sol만 사용할 때 캐시와 문맥을 유지하는 방법

### 추천: 고정 계획 fork + 마지막 통합 편집

고정 접두 P는 안정된 개발자 지시·도구 정의·공통 근거·계획 응답으로 구성한다. 각 작성 요청은 `P + 해당 단원의 작업`이다. 다른 섹션 초안·재시도 이력을 붙이지 않는다. 마지막에는 `P + 검증된 섹션 요약 + 충돌/누락 목록`으로 연결 편집을 수행한다.

이는 서버가 보관하는 영구 대화가 아니라 클라이언트가 보존한 문맥을 재전송하는 논리적 세션이다. 동일 session ID만으로 캐시나 대화가 유지되지 않는다. Luna와 Sol 사이의 모델 캐시는 공유하지 않는다.

캐시 계약:

1. 개발자 지시·도구·공통 입력의 순서와 직렬화를 고정한다. 시각·임의 ID·단계별 스키마를 공통 접두 앞에 넣지 않는다.
2. 동적 스키마·근거·작업 지시는 공통 접두 뒤에 둔다. 필요 없는 전체 스키마·전체 강의 중복 전송을 먼저 줄인다.
3. 지원되는 Responses 출력과 reasoning 항목은 원형대로 재전송한다. 도구 결과는 해당 `call_id`와 연결한다. 추론을 직접 복원하거나 모델 사이로 이식하지 않는다.
4. 현재 지원 설정인 explicit breakpoint·TTL·reasoning context를 유지하되 실제 endpoint와 ZDR 정책을 함께 검증한다. 모델명이 같아도 공급자가 달라지면 hit는 보장되지 않는다.
5. 계획 응답의 캐시 쓰기와 첫 작성의 캐시 읽기를 구분한다. 이번에는 첫 작성부터 읽기가 관측됐으므로 전체 첫 작성 완료를 기다리는 웜업 게이트가 필요한지 별도 A/B로 확인한다. 계획 출력 부분까지 캐시된 것으로 간주해 바로 제거하지 않는다.
6. cache read/write, uncached input, output/reasoning, 재시도 비용을 단계별로 기록한다. 캐시 적중률보다 품질을 통과한 완성 노트당 총비용을 판단 기준으로 삼는다.

특히 현재 `taskItem()`은 매 작업 끝에 explicit breakpoint를 붙인다. fork에서 다시 사용하지 않을 섹션별 입력까지 캐시 쓰기 대상으로 삼는지 확인해야 한다. **계획 뒤에 고정된 input_text 경계를 두어 P를 캐시하고, 일회성 작업 꼬리에는 경계를 두지 않는 방식**을 우선 비교한다. 공식 OpenAI 문서는 Sol 캐시 읽기를 일반 입력의 0.05배, 쓰기를 1.25배로 설명하지만 실제 OpenRouter 공급자 청구와 대조해야 한다. 캐시가 읽히더라도 초안 입력 약 44–50k 중 보고된 읽기 27.3k 밖의 부분과 출력·추론 비용은 남는다.

### 한 줄기 세션을 반드시 유지한다면

블록마다 호출하지 말고 의미상 연결된 단원 단위로 묶는다. 공통 P 뒤에 최근 단원 작업을 append-only로 추가하며 캐시된 접두를 수정하지 않는다. 예산에 가까워지면 검증된 핵심 주장·용어·미해결 문제로 명시적인 새 문맥 구간을 시작한다. 이때 과거 꼬리의 캐시·추론 연속성은 포기하는 것이므로 무손실 세션 유지라고 부르지 않는다. 정확히 같은 앞부분 P만 재사용 가능하다.

본문 상한을 키우는 것은 전송 실패 완화일 뿐 입력 누적 비용 해결이 아니다. cached input도 비용이 있고 새 출력·추론 비용은 남는다.

## 5. 다음 실험과 채택 기준

먼저 그림 연결·반복 설명·페이지 분리를 고친 동일 렌더러로 비교한다. 그다음 동일한 Sol 계획과 사람 기준 항목 목록을 고정하여 아래 3군을 반복 평가한다.

| 군 | 목적 |
|---|---|
| A: 전체 Sol fork + 통합 편집 | 품질 기준선 |
| B: Luna High 작성 + Sol 통합 편집·선택 수정 | 추천 가설: 품질을 유지하면서 Sol 출력량 절감 |
| C: Sol 계획의 배치 도구 → Luna 작성 → Sol 통합 편집 | 도구를 통한 위임 자체가 B보다 나은지 확인 |

고정 계획 실험은 작성 방식만 비교한다. 별도로 각자 계획부터 만드는 end-to-end 실험으로 전체 시스템 차이를 평가한다. 최소 여러 성격의 강의(개념·논증 / 수식·계산 / 도표·데이터), 반복 생성, 모델명을 가린 PDF 쌍대 평가를 사용한다.

품질은 원문 대비 정확성·핵심/조건/예외 보존, 개념 계층과 설명 순서, 비교·도식의 의미 정확성, 그림–본문 연결, 문제–답–근거 연결, 인쇄 가독성으로 평가한다. 잘못된 수식·관계·핵심 그림 누락은 비용으로 상쇄하지 않는 결함으로 둔다. 자동 coverage와 judge 점수는 보조 지표다.

**품질 차이가 실질적으로 없는 후보 사이에서 가격을 비교하고, 그다음 시간을 비교한다.** 아직 B의 품질 유지나 절감률은 미측정이며 $0.142에 검수 비용만 단순 더해 예측하지 않는다. 재작성량과 실패율이 함께 달라질 수 있다.
