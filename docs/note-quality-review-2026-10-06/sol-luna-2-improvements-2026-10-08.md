# sol-luna-2 노트 생성 엔진 개선 기획안

2026-10-08 · w/dev `2939407` 기준. 코드와 저장된 10월 7~8일 파일럿 보고서를 대조했다. 이번 검토에서 유료 모델 실험·운영 DB 변경·배포는 하지 않았다. 기존 미커밋 워크트리와 onboarding QA 파일은 건드리지 않았다.

## 목적과 결정 상태

**이번 산출물은 개선 기획안이다. 코드 수정·유료 실험·배포를 시작하는 승인이 아니다.** 우선순위는 품질 → 품질을 통과한 노트당 비용 → 소요 시간이다. 유지할 구조, 확인된 결함, 비교할 가설, 채택·중단 기준을 구분해 다음 구현 범위를 결정한다.

- **사용자 선호:** 2026-10-08 이전 리뷰 세션에서 `sol-luna-2-c.pdf`가 가장 마음에 든다고 밝혔다. 이 결과를 후속 설계의 품질 참고물로 삼는다. 선호 이유를 구조·내용·시각 표현 중 하나로 추정하지 않으며, 블라인드 점수나 모든 강의에서의 우월성으로 확대하지 않는다.
- **확인된 기준선:** 현행 Sol 계획·편집 / Luna High 초안·문항 / Sol 검수·수리의 역할 분담과 고정 접두 P를 출발점으로 유지한다. 제품 비교 기준인 `independent`도 남긴다.
- **권고안:** 계약·관측을 먼저 바로잡고, 같은 모델에서 작업 입력과 수정 단위를 줄이는 실험을 한다. 그다음 모델 배치·캐시·표현 방식을 각각 비교한다. 이것은 구현 완료 또는 효과 입증을 뜻하지 않는다.
- **이번 범위 밖:** 신규 SDK 도입, 엔진 전면 재작성, 기본 모델 자동 교체, 운영 설정·계정 변경, 보관함 저장 오류 수정. 저장 실패는 별도 제품 결함으로 남기며, 생성 성공과 파일 전달 성공을 혼동하지 않는다.

## 결론

1. 공급자 접두 캐시는 이미 실측으로 작동한다. 우선순위는 **수정 횟수·수정 입력/출력 감소 → 로컬 재개 캐시 → Luna 공통 접두 재사용**이다.
2. 의미 초안 → 코드 컴파일은 이미 구현됐다. 예시 PDF에 가까워지려면 **의미 관계와 지면 연결을 명시하고 HTML 본문+SVG 도해+KaTeX 수식을 조합**해야 한다.
3. 작성 후 무조건 compact하는 것은 추천하지 않는다. **계획 단계의 구조화된 메모리로 짧은 검수 문맥을 만들고, 오류 대상과 근거만 보내는 방식**을 먼저 비교한다. 공급자 native compaction은 별도 실험이다.
4. 검수 출력 계약과 적용 코드가 어긋나는 경로부터 고친다. 적용 불가능한 피드백은 모델을 바꾸거나 토큰을 늘려도 해결되지 않는다.

- `lib/section-draft.js`: 의미 주장·관계 → B01–B18 컴파일러가 이미 존재한다. 이를 다시 신설할 필요는 없다.
- `server/usage.js:43`: 시도별 cache read/write, reasoning tokens, 모델·공급자·비용 기록도 이미 있다. 전부 새로 설계하지 않는다.

## 3. 전체 과정의 캐시 개선

### 3.1 로컬 결과 캐시: 호출하지 않는 절약

실험의 cold-run 모드와 제품의 resume 모드를 분리한다. 캐시 on/off를 모델 구성과 묶지 않는다.

| 단계 | 재사용 조건 | 무효화 조건 |
|---|---|---|
| 정제/등록부 | 인식 자료 revision·정제 버전 동일 | 인식/원천 변경 |
| Plan/Editorial | 근거·정책·모델·프롬프트/계약 동일 | 자료·학습 목표·계획 변경 |
| 섹션 초안 | 해당 섹션 근거·편집 명세·실제 선수 주장 동일 | 해당 의존성 변경 |
| 검증 | 주장+정확한 근거 집합+검증기/판정 정책 동일 | 문장·근거·기준 변경 |
| 렌더 | 확정 Note·자산 revision·폰트/디자인/렌더 버전 동일 | 표시 요소 변경 |

암호화된 typed 산출물만 체크포인트로 남기고 평문 서버 결과 캐시를 도입하지 않는다. P와 editorial이 지금은 실행 메모리 전용이므로 bypassCache만 끄면 안 된다. 재개에 필요한 구조화된 상태의 보존 계약부터 정해야 한다. 공급자 encrypted reasoning을 다른 모델의 메모리로 해석하거나 임의 가공하지 않는다.

‘재개’는 완료 작업 재사용, ‘다시 생성’은 generationRevision 변경, ‘디자인만 변경’은 모델 호출 없이 재렌더로 구분한다. 한 섹션 수정 시 전체 계획/모든 섹션을 무효화하지 않도록 의존성 단위 키를 사용한다. 비용 청구용 requestId와 내용 재사용 cacheKey는 별개다.

### 3.2 공급자 prompt cache: 반복 문맥을 싸게 읽기

- 현재 Sol의 P는 그대로 재사용되어 실제 hit가 난다. 더 높은 hit ratio만 추구하지 않고 절대 입력량·캐시 미적중 입력·출력/추론량·실제 비용을 같이 본다.
- review/global/repair가 모두 원자료·계획 이력을 포함한 P를 필요로 하는지 나눈다. 특히 블록 수정은 **짧은 수리 지시 + 해당 편집 계약 + 해당 근거 + 오류 블록**으로 충분한지 비교한다.
- Luna는 독립 호출이지만 공통 접두 캐시를 쓸 수 없는 것은 아니다. 안정된 시스템 지시·스키마·공통 용어를 앞에, 섹션별 근거/명세를 뒤에 둔다. 실제 모델/공급자 지원과 prefix token 하한을 합성 probe로 검증한다.
- 각 요청의 순서·직렬화·스키마 변형도 접두 일치에 영향을 줄 수 있다. 문구를 매번 동적으로 바꾸거나 타임스탬프·섹션 ID를 공통 부분 앞에 넣지 않는다.
- 근거 없는 캐시 warmup 호출을 추가하지 않는다. 실제 필요한 첫 호출로 warm하고, 병렬 cold 호출과 첫 응답 후 병렬 호출의 비용/지연을 비교한다.
- cache write/read가 미보고면 null을 유지한다. 0과 구분하고 기존 usage_attempts의 실제 비용을 사용한다. 캐시 적중률이 높아도 전체 원문 반복량이 크면 비쌀 수 있다.

### 3.3 세션별 메모리 분리

P를 그대로 전달하는 것은 ‘작은 메모리 전달’이 아니라 큰 문맥의 재전송이다. 다음 세 층으로 나눈다.

- **편집 메모리:** 용어 표준, 개념 소유 섹션, 필수 조건/예외, 관계, 금지 사항, 검증 기준. 기존 editorialPlan에서 코드로 추출.
- **근거 저장소:** 로컬 암호화 evidence registry. 필요할 때 해당 근거를 메모리로 읽어 요청에 넣는다.
- **실행 상태:** 작업 revision, 성공/실패, 오류 서명, 검증 결과, 비용 예산. 모델 대화 밖에서 코드가 관리.

검수 전용 새 세션에는 첫 번째와 작은 작업 패킷을 전달한다. 대화 전체·추론 이력·모든 초안을 복사하지 않는다. 새 session_id만 만들고 같은 긴 입력을 보내면 비용은 줄지 않는다.

## 4. 예시 PDF 같은 정보 구조와 렌더링

핵심은 ‘HTML을 잘 그리라’는 지시보다 **설명 관계를 먼저 명시하는 것**이다. 기존 page-design-spec과 B/P 에셋은 재사용한다.

| 정보 구조 | 작성 계약 | 렌더 방식 |
|---|---|---|
| 개념 | 정의·쉬운 설명·조건·예외·적용을 구분 | HTML 제목·속성 행·본문 |
| 비교 | 동일 기준×대상, 미확인 칸 구분 | 실제 HTML table, 인쇄 머리 반복 |
| 인과/논증 | 전제·근거·결론·반론, 간선별 의미/근거 | SVG 도식 + 텍스트 설명 |
| 역사/절차 | 순서·분기·전환 조건 | SVG 타임라인/흐름도 |
| 사례 | 관찰 단서→개념 적용→판단→한계 | HTML 사례 상자·Point 연결 |
| 수식/그래프 | 원식 ID·변수·가정·단위·검산·해석 | KaTeX + 검증 데이터 기반 SVG |
| 점검 | 본문 개념 참조·질문·답·해설 | HTML 문항과 해설, 상호 링크 |

### 컴파일러 개선

현재 `lib/section-draft.js:169`는 같은 유형의 관계를 배열 순서로 계획 블록에 배정한다. 중간 관계가 빠지면 다음 관계가 앞 슬롯에 연결되는 위험이 있다. 실제 손실 규모는 추가 계측이 필요하지만, 관계마다 안정된 `relationId`와 `targetBlockId`/`learningItemIds`를 명시하면 대응이 검증 가능해진다.

- 모든 생성 주장·관계는 included/merged/deferred/unmapped 상태를 가진다. 블록 수와 배열 상한 때문에 남은 의미 항목을 조용히 버리지 않는다.
- 내용이 없는 고정 상자를 채우게 하지 않는다. 필요한 정보가 있는데 기존 템플릿에 안 맞으면 분할하거나 적합한 표현으로 전환한다.
- 한 개념의 핵심 조건·예외를 잘라 곁설명으로 보내지 않는다. 작은 여백 칼럼에는 본문 없이도 이해되는 보조 설명만 둔다.
- 각 섹션은 ‘학습 질문 → 설명 → 관계/자료 → 적용’을 기본으로 하되, 모든 섹션에 모든 종류를 강제하지 않는다.

### HTML/SVG를 만들어 붙이는 방법

추천은 **모델이 VisualSpec JSON을 만들고 코드가 HTML/SVG로 렌더한 뒤 Note에 결합**하는 방식이다. 예:

```json
{"visualId":"V1","kind":"argument_map","targetBlockId":"S2_B3","nodes":[{"id":"n1","claimId":"c4"},{"id":"n2","claimId":"c8"}],"edges":[{"from":"n1","to":"n2","relation":"supports","evidenceIds":["U4.t2"]}]}
```

노드 이름·주장 내용은 기존 원장에서 읽고, 간선의 사실성·참조를 먼저 검사한다. 좌표·색·줄바꿈·화살표는 렌더러가 결정한다. 사용자 자료나 모델 출력의 스크립트·외부 URL·임의 HTML은 실행하지 않는다.

전체 노트를 PNG로 붙이면 검색·선택·접근성·수식 선명도가 나빠진다. 본문은 HTML 텍스트로 유지하고 구조 도해만 SVG로 삽입한다. 원본 이미지가 필요한 곳은 허용된 figure/table/formula 크롭을 사용한다. 보조 개념도에는 내용과 같은 텍스트 대체 설명을 제공한다. 숫자가 없는 자료에 가짜 통계 그래프를 만들지 않는다.

출력 검수는 DOM 크기·overflow·수식 오류·이미지 완료·고아 제목·표 분할을 먼저 코드로 검사한다. 시각 모델 검수가 필요하면 실패한 도해/지면 영역만 별도 동의 범위에서 보낸다. 개발용 인쇄 검수는 합성 fixture로 수행하고, 실제 강의 평문 PDF를 서버에 보관하는 구조로 바꾸지 않는다. 페이지를 맞추기 위해 내용 축약을 자동 실행하지 않는다.

## 5. 저비용 피드백 루프

### 추천 순서

1. **코드 사전검사:** 스키마·ID·빈 필수 항목·숫자/단위·수식·그림 연결·coverage/누락 관계를 검사한다. 이 결과로 작업 목록을 만든다.
2. **불필요한 수정 제거:** 원문 근거 없음은 새 문장을 계속 만들 사유가 아니다. 불확실성으로 보존한다. 형식 정규화와 렌더 문제는 코드로 고친다.
3. **대상 한정 수리:** 동일 섹션·같은 원인을 소규모 묶음으로 보내고, 수정 부분만 반환한다. token 상한을 예상 출력량 기준으로 정한다. 수정 한 문장에 전체 블록을 재출력하지 않는다.
4. **단계별 모델 배치:** 단순 형식/용어는 코드 또는 Luna, 복합 논증·모순·수학적 설명은 Sol. 모델 변경은 명시적 새 정책으로 실험하며 기존 sol-luna-2 계약을 몰래 바꾸지 않는다.
5. **전역 검수:** 검증된 개념/관계 인덱스와 unresolved 목록으로 중복·모순·누락 연결을 찾는다. 의심 항목에만 원문 근거·전체 주장을 추가 공급한다.
6. **변경분 검증:** 바뀐 주장과 의존 closure만 검사하고 동일한 오류 서명이 반복되면 멈춘다. 섹션 전체 재작성은 마지막 수단으로 예산과 필수 검증을 적용한다.

입력 패킷 예: `policyVersion, baseRevision, targets, currentText, exactEvidence, neighborClaims, errorCodes, allowedOps, remainingBudget`. 출력은 `accepted patch candidates + unresolved reason codes`다. 자연어 자기반성 보고서·전체 노트 재출력은 요구하지 않는다.

현재 globalSections는 주장 문자열을 600→300→200→160자로 잘라 입력량을 맞출 수 있다(`lib/stages.js:118`). 이런 문자 절삭은 조건·부정을 잃을 수 있다. 검수 패킷은 **완전한 주장 일부를 선택**하고, 생략한 ID 목록을 남기며 필요한 경우 원문을 추가 조회한다. 부분 문장을 완전한 주장처럼 검수시키지 않는다.

### 무조건 compact와 새 검수 세션 비교

| 방식 | 평가 |
|---|---|
| 작성 끝나면 항상 LLM compact | 추가 호출·입출력·요약 손실·새 prefix warm 비용 발생. 현재처럼 P가 고정된 구조에서 기본 채택 근거 부족 |
| 기존 P를 유지 | 이미 hit 실측 있음. 전체 맥락이 꼭 필요한 전역 판단의 기준선으로 유지 |
| 코드로 editorial/검증 결과를 선택해 새 검수 패킷 구성 | 추가 요약 호출 없이 크기를 줄일 수 있어 1순위 |
| LLM이 짧은 구조화 handoff를 한 번 작성 | 여러 후속 작업이 같은 메모리를 반복 쓸 때 후보. ID·조건·예외 보존 검사 필수 |
| 공급자 native compaction | opaque compaction item을 받아 재사용하는 별도 기능. OpenAI 직접 API 문서만으로 현재 OpenRouter 경로 지원을 보장하지 않음 |

현재 note-session의 item whitelist/고정 anchor 검증도 native compaction item에 맞춰 검토해야 한다. 기존 encrypted reasoning item을 임의로 compact item이라고 바꾸지 않는다.

손익 비교는 `압축/메모리 생성 비용 + 새 prefix 준비 비용 + Σ축소된 후속 호출 비용 < Σ기존 후속 호출 비용`일 때만 이득이다. cached input도 별도 단가를 가지므로 단순 토큰 수 감소율과 비용 절감률은 다르다. 이 식에는 추가 지연, 검증 실패, 재수정 비용도 포함한다.

## 6. 실행 우선순위와 실험

### P0: 실패하는 계약과 관측부터

- review operation 필드 일치, 제안→실제 적용까지 end-to-end 테스트.
- 반려 사유 및 actual accepted 통계, redo 이후 검증 일관성.
- 수정 원인을 writer-null / compiler-unmapped / schema / support / review-redo로 분리. 출력과 reasoning token도 분리 보고하며 공급자 output 합계에 reasoning이 포함되는지 확인해 이중 집계하지 않는다.

### P1: 가장 큰 비용인 repair 축소

- 동일 plan/editorial/초안을 고정한 상태에서 full-P Sol repair와 짧은 RepairPacket Sol repair를 비교한다.
- 이후에만 단순 수리 Luna→필요 시 Sol과 Sol 단독을 비교한다. 입력 축소와 모델 교체를 동시에 바꾸지 않는다.
- 비용/주장 복구, 비용/실제 채택 수정, 필수 항목 보존, 잘못된 승인/보류, p50/p95 지연을 측정한다.

### P2: 캐시 제품화·정보 구조

- cold 실험과 warm 제품 재개 분리, 암호화 산출물 재사용.
- 관계의 명시적 블록 대응과 unmapped 추적, VisualSpec→HTML/SVG 렌더.
- 같은 Note를 사용해 디자인만 A/B 평가하고, 의미 내용 변화와 시각 효과를 분리한다.

### P3: 선택적 compaction 실험

- code-selected handoff / LLM handoff / full P / 지원 확인된 native compact를 비교한다.
- 1개/3개/여러 후속 검수·수정 작업에서 break-even을 확인한다. 실제 반복이 적으면 생략한다.

평가는 인문 논증·경영 비교·경제 계산·인식 결손을 포함한다. 사람 블라인드 품질 점수와 오류 검토 없이 가격만으로 승자를 정하지 않는다. 먼저 기존 파일럿과 같은 강의/초안을 사용하는 수정 실험으로 원인을 분리하고, 그다음 여러 강의 end-to-end로 일반화한다. 이번 제안의 절감률은 아직 미측정이다.

## 7. 추가 코드 검토: 프롬프트·컨텍스트·루프 제어

### 단계별 프롬프트가 너무 많은 역할을 공유한다

`server/prompts.js:146`은 모든 단계에 COMMON+NOTE_RULES를 넣는다. 따라서 repair/review도 모든 B유형·문항·지면 슬롯 규칙을 받는다. 한국어, 보강 옵션 off, v2 기준 시스템/단계 지시의 UTF-8 크기는 plan 9,390 / editorial 7,894 / draft 10,087 / repair 8,116 / review 8,359 / questions 7,745 bytes다. 실제 공급자 토큰 수는 아니며 JSON 스키마·자료는 제외했다.

개선은 공통 접두에 출처/신뢰 경계·숫자/조건 보존·출력 정책을 짧게 고정하고, 단계에는 해당 역할만 넣는 것이다. Draft에는 현재 섹션 관계 종류와 완결된 설명 기준, repair에는 오류와 허용 변경, review에는 operation별 의미·채택 조건을 준다. ‘잘 생각해라’ 같은 추론 지시나 장문의 자기검토 출력을 추가하지 않는다.

Luna는 짧은 정상 예시와 반례를 해당 역할별로 제공하는 실험을 한다. 예: 원문의 조건을 빠뜨린 요약, 순서를 인과로 바꾼 도식, 없는 비교 칸을 채운 사례. 예시는 합성 자료이며 변하지 않는 접두에 놓는다. 예시 수나 성능 향상률은 측정 없이 확정하지 않는다.

Sol v2는 `text.format=json_object`로 JSON 형식만 요청하고, 출력 스키마를 작업 텍스트에 싣는다(`server/note-session.js:202,322`). Luna의 strict structured output과 같지 않다. 현재 제공자에서 native json_schema를 지원하는지 probe한 뒤, 단계별 schema enforcement가 형식 실패·접두 재사용·지연에 미치는 영향을 비교한다. 캐시를 위해 형식 실패 비용을 계속 감수하는 것이 유리한지는 실측 문제다.

### RepairPlan 모듈의 기능과 실제 실행 연결을 구별해야 한다

`RepairBudget.record()`와 `nextRepairStep()`의 오류 서명 비교는 구현돼 있다. 그러나 재검증에서 어댑터는 `nextRepairStep({failures,budget})`만 호출하고(`lib/stages.js:46-57,670,849`), `budget.record()` 호출은 stages.js 전체에 없음을 확인했다. `attemptsByTargetCause`·`spentUsd`·`successfulTargets`가 영구 0이므로 `canAttempt`의 per-target·per-cause 상한은 무력하고(`lib/repair-plan.js:353,382`), `signatures` 맵도 전달되지 않아 동일 서명 중단(`repair-plan.js:303-312`)이 발동하지 않는다. `maxUsd`는 미지정으로 Infinity다(`repair-plan.js:132-133`). 제어기가 상태를 알아서 축적하지는 않는다.

로컬 순수 함수 확인에서도 같은 요청을 두 번 주면 regenerate_missing이 두 번 반환되고 기록 0/사용액 0/maxUsd 무한으로 남는다. 이것은 이 모듈의 호출자가 결과를 기록해야 한다는 증거다. 실제 제품에 무한 루프가 있다는 뜻은 아니다. 묶음 상한 12, repair 1회+ALT 2차 1회, redo ≤2(`stages.js:679,700-719,1033`) 같은 구조적 상한이 별도로 존재한다.

관측 경로도 끊겨 있다. `stages.js:1185`의 `loopMetrics(loopBudget)`는 이벤트 배열을 기대하는 `metricsOf(events = [])`(`lib/repair-plan.js:405`)에 budget 객체를 넘기고, `Array.isArray` 정규화(`:418`)에서 비배열은 `[]`가 되므로 `BLOCKS_HELD` 로그에 붙는 loop 지표는 항상 0이다. 실제 이벤트 수집·전달과 집계 테스트를 연결해야 한다. 로그 제거만으로 관측이 복구되지는 않는다.

수정 방향은 `reserveAttempt → execute → record(actual cost, error signature, input revision, improvement) → commit/rollback`의 한 실행 계약으로 연결하는 것이다. 네트워크 재시도, 같은 내용 재작성, 다른 근거로 재검증을 구분하고 병렬 호출은 예약 비용까지 합쳐 검사한다. 마지막으로 검수 operation부터 재검증까지 통과하는 통합 테스트를 둔다.

review 수정 계약도 같은 원칙으로 정리한다. 스키마를 무한정 확대하는 방향이 아니라, producer(`lib/note-contract.js` 출력 스키마)와 consumer(`lib/stages.js` 적용기)가 하나의 계약 정의를 공유하도록 정렬하고, operation별 허용 필드는 그 단일 계약에서만 선언한다. `assetIds`/`figureIds` 불일치(`note-contract.js:601` vs `stages.js:996`)와 스키마에 없는 `from/to/value` 요구(`stages.js:1005-1022`)는 필드 추가로 메우기 전에 어느 한쪽이 계약의 원천인지부터 정한다.

### Luna 캐시는 이미 일부 준비돼 있다

`server/llm.js:33–43`에는 Luna 변형의 explicit 캐시와 concepts/options/allowedRefs 공통 user 접두를 분리하는 코드가 있다. ‘공통 접두 구현을 새로 시작’보다 실제 전송 순서·동적 참조 목록·지원 경로·길이·cold 병렬 호출을 진단하는 것이 먼저다. 파일럿의 cache-read 0은 코드 부재나 모델의 캐시 불가능을 증명하지 않는다.

## 8. 에이전트화 평가

현재 파이프라인은 고정 단계 + 섹션 병렬 작성 + 조건부 수리·재검증으로 이뤄진 agentic workflow다. 목표만 주고 도구 선택과 계획을 모델이 스스로 정하는 자유형 자율 에이전트가 없다는 것 자체는 문제가 아니다 — 검증 가능한 단위, 결정론적 재개, 비용 상한이 지금 구조의 강점이다. 에이전트 SDK 전면 도입이나 런타임 재작성은 제안하지 않는다.

대신 현재 workflow 안에 에이전트 패턴을 점진적으로 실험할 후보를 둔다.

| 후보 | 내용 | 기대 |
|---|---|---|
| 공통 plan + 독립 작업 packet | plan/editorial은 공유 읽기 전용으로 두고 각 섹션·수리 작업은 자급 packet(targets, 근거, 허용 op, 남은 예산)으로 실행 | 병렬성 유지, 작업별 독립 재시도 |
| baseRevision 기반 patch commit | 모델은 전체 재출력 대신 patch 후보만 내고, 호스트가 baseRevision을 확인해 원자 적용·실패 시 원복 | 부분 실패 격리, 경쟁 변경 감지 |
| 코드 선검증 | 스키마·ID·필수 항목·근거 연결을 모델 호출 전에 코드가 검사해 작업 목록 생성 | 불필요한 모델 호출 감소 |
| 성공 section 암호화 resume | 성공한 섹션 산출물만 암호화 체크포인트로 보존하고 실패분만 재실행 | 재실행 비용 절감 |
| 내용없는 cache metrics | 단계별 cache read/write·hit를 내용 없는 지표로만 기록 | 접두 캐시 설계의 실측 근거 |

이 후보들은 채택이 확정된 설계가 아니라 실험 대상이다. ‘작성 후 무조건 compact’ 역시 금지 규칙이 아니라 5절 비교표 안에서 같은 실험으로 다룰 후보로 둔다. 채택 여부는 6절의 비용/품질 실험으로 정한다.

## 9. 의사결정안과 구현 인계 조건

### 9.1 접근법 비교

| 접근 | 장점 | 비용·위험 | 기획 판단 |
|---|---|---|---|
| 현행 workflow 안에서 계약·검증·작업 packet 개선 | 선호 결과를 만든 모델 배치 유지, 원인별 효과 분리 가능 | 작은 packet에서 필요한 근거를 누락할 수 있어 선택·추가조회 검사 필요 | **우선 권고**. P0를 통과한 뒤 P1 실험 |
| 작성 후 짧은 인계 정보 또는 compaction으로 검수 문맥 재구성 | 반복 검수·수정의 입력량 감소 가능 | 요약 손실, 압축 호출비, 새 접두 준비 비용. 현재 경로의 native 지원 미확인 | 조건부 비교군. code-selected handoff를 먼저 비교하며 무조건 compact는 기본값으로 두지 않음 |
| 자유형 에이전트·SDK 중심으로 전면 전환 | 모델이 작업·도구 순서를 유연하게 선택 | 계약·예산·동의·상태 소유권을 다시 검증해야 하며 현재 문제 해결의 추가 이득 미입증 | 현 단계 보류. 기존 workflow로 해결할 수 없는 구체적 실패가 확인될 때 재검토 |

### 9.2 단계별 책임과 인계

기획의 핵심은 에이전트 수가 아니라 **각 단계가 무엇을 읽고 무엇을 확정할 권한이 있는가**다. 아래는 목표 계약이며 현행 구현과의 차이는 2·7절에 기록했다.

| 책임 | 입력 | 출력·확정 권한 |
|---|---|---|
| Sol 계획·편집 | 승인된 강의 근거와 학습 옵션 | 섹션/학습 항목·용어·관계·필수 조건·선행 의존성. 원문에 없는 필수 사실을 새로 만들지 않음 |
| Luna 섹션 작성 | 해당 편집 명세·정확한 근거·검증된 선행 주장 | 의미 초안과 근거 참조. 공통 계획이나 다른 섹션을 직접 변경하지 않음 |
| 코드 컴파일·사전검사 | 의미 초안·계획·등록부 | 표현 블록, 누락/미매핑 목록, 형식·참조 오류. 사실의 옳음을 형식 통과로 대체하지 않음 |
| Jev 및 근거 검증 | 완전한 주장과 그 주장의 정확한 근거 | 지지/보류 판단. 무응답·검사 실패는 무근거 판정과 구분 |
| Sol 수리·통합 검수 | 허용 대상·현재 revision·관련 근거·오류/미해결 목록 | 제한된 수정 후보. 입력에 없는 항목은 추가조회 또는 미판정으로 남기며 전체 노트 변경 권한 없음 |
| 호스트 적용·렌더 | 수정 후보·현 revision·검증 결과 | 충돌 확인 → 임시 적용 → 필수 재검증 → 확정/원복. 확정 Note만 렌더하며 외부 스크립트·임의 HTML 실행 금지 |

입력에 수식·그림·조건이 보이지 않아 검수하지 못한 것과, 노트에 실제로 그 내용이 누락된 것은 다른 문제다. `REVIEW_UNRESOLVED`를 곧바로 재작성 지시로 바꾸지 않는다. 먼저 해당 ID의 완전한 정보가 제공됐는지 확인하고, 필요한 근거를 공급할 수 없으면 미판정으로 보존한다.

### 9.3 구현 착수 후 통과해야 할 단계

| 단계 | 산출물 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| P0 계약·관측 | operation별 합성 계약 테스트, 반려 사유, 실제 채택 수, 복구 시도·서명·비용 연결 | 지원 operation은 정상 입력으로 적용 가능하고 잘못된 대상·revision·근거는 거절/원복. redo도 같은 필수 검증을 거치며 큐 등록을 채택으로 집계하지 않음 |
| P1 수정 입력 축소 | 동일 plan/editorial/draft에서 full-P Sol 대 RepairPacket Sol 비교 | 조건·예외·근거를 보존한 실제 수정이 채택되고 사람 평가에서 품질 회귀가 없음. 총비용은 추가조회·재수리·실패 호출까지 합산 |
| P2a 결과 재사용 | 암호화 산출물·의존성 키·무효화/복원 테스트 | 동일 입력 완료분은 재사용하고 근거·계획·정책 변경분은 무효화. 저장되지 않은 P/editorial을 있는 것처럼 재개하지 않음 |
| P2b 정보 구조·표현 | relation→block 대응, 미매핑 보고, 동일 Note의 표현 비교 | 의미 항목의 조용한 유실 없음. 지원 템플릿으로 표현할 수 없는 항목을 임의 삭제하지 않음. overflow·수식·그림 참조·텍스트 대체 설명 검사 통과 |
| P3 문맥 압축 | full P / 코드 선택 / LLM handoff / 지원 확인된 native compact 비교 | 품질을 통과한 비교군에서 실제 후속 호출 수를 기준으로 압축·캐시 준비·재수리까지 포함한 비용 이득 확인 |

P2a와 P2b는 서로 다른 변경이다. 한꺼번에 묶어 품질·비용 효과를 주장하지 않는다. P0에도 사용자에게 전달되는 파일 저장 성공은 포함되지 않으므로, 별도 저장 결함이 열려 있으면 실험 결과를 제품 전체 완료로 표현하지 않는다.

### 9.4 평가와 중단 규칙

- **비교 기준:** 제품 기준 `independent`, 현행 `sol-luna-2`, P0 수정 기준선을 구분한다. 과거 run C는 선호 참고물이고 통제 실험의 동일 입력 기준선은 아니다. 복구 입력 축소는 P0 기준선과 plan/editorial/draft·모델·effort·검증 정책을 고정해 비교한다.
- **품질 평가안:** A/B 라벨을 가리고 정확성·설명 구조·조건/예외 보존·누락/중복·시각적 이해를 각 1~5점으로 평가한다. 필수 조건 누락, 무근거 사실·관계 추가, 수식 의미 오류는 평균 점수와 별개로 탈락 사유다. 비열등성 허용폭·평가자·표본 수는 실행 전 승인받으며, 미정이면 우열 판정 없이 탐색 결과만 보고한다.
- **비용 지표:** run의 성공·실패 호출 전체 비용, 실제 채택 수정당 비용, 품질 통과 노트당 비용을 구분한다. 품질 통과 노트가 0이면 마지막 지표는 n/a다. 근거 지지 주장 수·coverage·cache hit만으로 품질 통과를 판정하지 않는다.
- **예산 제안:** 기존 파일럿의 run당 $1.50와 합성 probe 단계 총 $0.05를 출발 상한으로 제안한다. 신규 실험 총예산·군 수는 별도 승인 전 미집행이다. 호출 전 예약 비용과 누적 비용으로 상한 초과가 예상되면 새 호출을 시작하지 않고, 취소·실패 호출도 원장 대조에 포함한다.
- **중단:** plan/editorial 실패 1회, 연속 상류 429 2회, 예산 초과 예상, 동의·저장·보호 조건 위반 시 해당 실험을 중단한다. 같은 대상·입력 revision·오류 서명에 개선이 없으면 추가 의미 수리를 멈추고 미해결로 남긴다. 예산을 넘기며 완주를 강제하지 않는다.
- **재실행 구분:** 실험에서는 실패 원인을 고치고 싼 검증을 통과한 뒤 새 run으로 실행한다. 실패한 동일 arm을 변화 없이 반복하거나 멈춘 run을 이어 붙이지 않는다. P2a의 제품 재개 기능은 별도 합성 검증 대상으로, 이 실험 운영 규칙과 혼동하지 않는다.

### 9.5 기획 완료와 후속 승인

이번 기획안의 결과는 **권고 방향과 실험 계약**이며 절감률·품질 향상 수치는 약속하지 않는다. 구현 승인 시 첫 범위는 P0로 한정하고, P1 이후는 P0 결과를 보고 각각 선택한다. 구현 승인만으로 배포·유료 실험·운영 DB 변경까지 승인된 것으로 취급하지 않는다. 사용자 선호 run C를 유지하고 싶은 이유는 다음 사람 평가에서 함께 확인하되 지금 임의로 확정하지 않는다.

## 이번 검토의 검증 상태

- 기존 검토 기록의 회귀 게이트: 1,405 tests, 1,404 pass, 0 fail, 1 skip. 현재 테스트가 위 operation 불일치를 모두 검증한다는 뜻은 아니다.
- 기획안 보완 후 로컬 재검증: `node --test --test-reporter=dot lib/*.test.js server/*.test.js tools/*.test.mjs` 종료 코드 0. 기획의 품질·비용 효과를 검증한 실험은 아니다.
- CWS dry-run 재검증: `node tools/package-cws.mjs --dry-run --skip-tests` 종료 코드 0, 93개 엔트리 검사 통과. 위 단위 테스트는 별도 실행했으며 ZIP 생성·배포·업로드 없음.
- 공식 문서 조사와 에이전트 설계 리서치는 최신 리서치 부록인 [agent-context-research-2026-10-08.md](agent-context-research-2026-10-08.md)를 참고한다. compaction을 무조건 하지 말자는 결론은 현재 구조·비용에 대한 본 제안의 판단이다. 문서가 모든 작업의 compaction을 명시적으로 금지한다고 해석하지 않는다. 지정된 OpenRouter 캐시 문서에서 native compaction 지원을 확인하지 못했으며 전체 서비스의 미지원으로 단정하지 않는다.
- 이 세션의 산출물은 개선안과 연결된 조사 부록이다. 런타임 변경은 하지 않았다. 비용 절감·설명 품질 향상은 새 실험을 거쳐야 한다.
