# 노트 품질 후속 검토와 캐시 개선안

2026-10-07. 기준: `proposal.md`, `05913cc` 및 현재 미커밋 진단 변경. 코드 검토는 합성 fixture와 요청 계약을 사용했다. 실제 강의 식별자·본문·키는 이 문서에 포함하지 않는다.

## 판단

작성 모델은 **Luna High를 우선 실험 후보**로 둔다. 현재 운영 기본을 바꾼 것은 아니다. 문항 요청의 전송 결함을 먼저 고친 뒤 재측정해야 한다. 계획·폴백 모델은 현재 모두 `openai/gpt-6.1-sol`이다. 같은 모델을 다시 부르는 것만으로 계획 캐시가 재사용되지는 않는다.

기획 P0~P3는 상당 부분 코드로 연결돼 있지만 완료 기준에는 미달한다. 특히 요청 직렬화 누락, 캐시·비용 계측, 의미 커버리지 및 인쇄 검증을 우선 보완한다. 회귀 테스트 통과와 사람에게 유용한 노트 품질은 별도 판단이다.

## 기존 실험에서 관측된 것

출처: 로컬 자동 디버그 세션의 작성 모델 실험 요약과 서버 비용 집계 보고. 같은 강의 1건의 탐색 실험이며 독립 반복 표본이 아니다. 비용은 이 검토에서 서버 원장을 재조회한 값이 아니라 디버그 세션 보고값이다.

| 작성 모델 | 총 시간 | 최초 판정 주장 | 최종 유지 주장 | 유지 섹션 | 비용 보고 |
|---|---:|---:|---:|---:|---:|
| Mimo Flash | 4.9분 | 88 | 85 | 5/6 | 약 $0.22 |
| Luna Medium | 3.5분 | 49 | 40 | 5/6 | 약 $0.06 |
| Luna High | 9.2분 | 74 | 71 | 6/6 | 약 $0.09 |
| Luna XHigh | 15.5분 | 68 | 63 | 5/6 | 약 $0.82 |

- Mimo는 로컬 결과 캐시가 많이 적중해 시간 비교 기준으로 부적합하다.
- High는 전 섹션이 유지됐지만 120초 타임아웃 2건이 있었다. 유지 주장 비율은 사실 정확도나 원문 대비 학습 내용 보존율이 아니다.
- XHigh는 Sol 폴백 3회가 약 $0.653을 차지했다고 보고됐다. 입력 캐시만 개선해도 비싼 출력·추론 토큰 비용은 남는다.
- 모든 실험에서 문항 단계 400 오류가 있었으므로 완성 노트의 품질 비교로 간주하지 않는다.
- Luna의 캐시 읽기/쓰기 0이라는 기존 보고는 공급자 원본 사용량과 정규화 계층을 다시 대조해야 한다.

## 최우선 수정안과 완료 기준

### 1. 실제 HTTP 요청에 기획 필드를 전달

`lib/service-client.js`의 `write()` 직렬화가 `blockId`, `allowedRefs`, `learningItems`를 누락한다. `server/prompts.js`의 questions 계약은 `blockId`를 필수로 요구하며 서버가 모델 호출 전에 거부한다. 합성 fetch로 `ServiceClient.write({stage:'questions', blockId:'S1_B2', ...})`를 실행해 세 필드 모두 전송되지 않음을 재현했다.

- 수정: 단계별 허용 필드를 명시적으로 전달하되 임의 옵션 전체를 spread하지 않는다. 기존 dirty 진단 변경은 보존한다.
- 검증: pipeline→ServiceClient→서버 요청 검증을 실제 직렬화까지 통과시키는 합성 테스트를 추가한다. `ServiceClient`를 우회하는 service mock만으로 통과시키지 않는다.
- 완료: questions 400 해소, 생성 가능한 fixture에서 B14 문항·해설과 살아 있는 본문 참조 검증 통과. allowedRefs와 learningItems도 HTTP 본문에서 확인한다.

### 2. 캐시 관측부터 정확하게

`server/llm.js`의 `cacheOf()`는 최상위 `cache_creation_input_tokens`/`cache_write_tokens`를 읽지만 `prompt_tokens_details.cache_write_tokens`를 읽지 않는다. 합성 입력에서 `cached_tokens:0, cache_write_tokens:2048`을 넣으면 쓰기 토큰은 `null`이 된다.

- 수정: 공식 응답의 중첩 필드와 기존 공급자별 필드를 정규화한다. 미보고 `null`과 확인된 `0`을 유지한다.
- 기록: 요청별 모델·실제 공급자·단계·시도·입력/출력/추론/캐시 읽기/쓰기·보고 비용을 콘텐츠 없이 남긴다. 추정 비용과 실제 보고 비용을 구분한다.
- 완료: 모의 응답의 null/0/양수 테스트, 동일 합성 접두부 cold/warm 실제 호출, 응답 및 generation 사용량 대조. 캐시 키를 보냈다는 이유만으로 hit라고 기록하지 않는다.

### 3. 캐시를 재사용할 요청 구조

현재 plan/write는 서로 다른 system 지시와 동적 `response_format`을 보내는 독립 호출이다. Sol 폴백은 이미 있지만 plan 대화를 전달하지 않는다. Luna 캐시를 Sol로 옮겨 쓸 수 있다는 가정은 하지 않는다.

- 우선안: 기존 Sol 계획 + Luna High 작성 + 실패한 작은 블록만 Sol 재작성. 같은 섹션 전체를 여러 번 쓰기 전에 크기 분할과 오류 종류를 확인한다.
- 같은 모델·공급자·안정된 지시/스키마/공유 자료 접두부를 맞춘다. 요청별 섹션 자료는 뒤에 둔다.
- `provider.order`를 지정하면 OpenRouter sticky routing이 꺼진다는 공식 조건을 검토한다. ZDR 공급자 allowlist는 유지하고, 단일 공급자 고정 또는 allowlist + 불투명 session routing을 실험한다. 모델/공급자를 사용자에게 알리지 않고 전환하지 않는다.
- 단계별 cache key는 plan→write 문맥 재사용을 분리할 수 있다. 같은 job이라는 이유만으로 모든 요청을 같은 key로 묶기보다 실제 공통 접두부/계약 버전/모델에 맞춘다. 내용 해시를 원격 ID로 보내지 않는다.
- planning 문맥을 매번 전체 전송하면 cached input도 과금될 수 있다. 캐시 적중률만이 아니라 노트 1건의 총비용·지연·실패 비용을 비교한다.

### 4. P0~P3 완료 주장 보정

| 항목 | 확인 결과 | 후속 완료 기준 |
|---|---|---|
| 보존 중심 T5 | 별도 복구 예산, 근거 재연결, pending 암호화 저장 경로 존재 | 사람 라벨로 false withhold/accept 비교. 보류 의존 주장도 확정 본문에서 분리 |
| 비교 화면 | records에서 support를 찾지만 지표 호출은 초기 supportScores/repairs 사용 | 암호화 기록만 로드해도 같은 주장 점수·복구 분모가 일치 |
| 비용 미측정 | admin 집계가 0에서 시작하여 미보고를 0원으로 내보낼 수 있음 | 관측 없는 비용은 null, 실제 0원과 구분 |
| 의미 초안 | claimId/dependsOn을 입력받지만 컴파일 시 본문 주장에는 유지하지 않음 | 로컬 ID/의존성/검증 상태를 별도 원장으로 유지하고 cascade에 연결 |

외부 검토의 오판도 바로잡았다. `figureFunnelStats`는 `lib/stages.js`에서 실제 호출된다. busy-provider 테스트는 이전 기록에서 실패했으나 이번 개별 재현과 전체 게이트에서는 통과해 확정 회귀로 분류하지 않는다.

## Sol 계획→작성 연속 실험

실험 도구는 합성 강의만 사용하며 운영 모델·서버 설정을 변경하지 않는다.

- A: 현재 방식처럼 Sol plan과 각 writer를 독립 호출.
- B: 최초 system·계획 입력·assistant 계획 응답을 유지하고 같은 Sol 대화에 작성 요청을 이어 붙임. 실제 공급자 세션에 서버 저장을 요구하지 않고 호출자가 history를 메모리에서 소유한다.
- 동일 fixture·옵션·effort·공급자 조건을 사용한다. B에서 안정된 JSON 응답 형식을 위해 upstream strict schema 적용 방식이 달라지면 이를 실험 교란 요인으로 명시하고 로컬 검증은 동일하게 유지한다.
- 계획 정규화, 모든 섹션 작성, 코드 검증, 전역 조립까지 실행한다. 첫 섹션 성공을 전체 완료로 보고하지 않는다.
- 요청 수·시간·비용 상한을 두고, 미보고 비용을 0으로 치환하지 않는다. 타임아웃을 자동으로 끝없이 재시도하지 않는다.
- 관측: 총비용, 단계별 지연, 입력/출력/추론 토큰, cache read/write, 실제 공급자, 블록/섹션/문항 생존과 검증 오류. T5/사람 품질 평가는 실행한 범위만 보고한다.

현재 서비스 API에는 history 입력 계약이 없어 별도 `tools/sol-session-bench.mjs`로 비교한다. 사용자가 지정한 로컬 env 파일에서 키를 실행 프로세스에만 주입했다. 키 값은 문서·로그·명령행 인자에 남기지 않는다. 단일 Azure 공급자, ZDR 및 데이터 수집 거부, 자동 공급자 폴백 금지 조건을 유지한다. 두 방식 합계 추정 예산 $2, 최대 16회, 요청당 120초로 제한한다.

### 실제 실행 결과와 한계

키 인증과 사용 한도는 정상으로 확인했다. 2026-10-07 직접 호출 결과는 아래와 같다.

| 명시 공급자 | 독립 호출 | 대화 연속 호출 | 결과 |
|---|---|---|---|
| Azure | 계획 단계 응답 불완전 | 계획 단계 응답 불완전 | 추가 단일 진단에서 HTTP 200 내부 `error.code=429` 확인 |
| OpenAI | `provider_error_404` | `provider_error_404` | 두 방식 모두 `no_endpoints` |

공급자 목록 조회 성공이 ZDR·파라미터 조건을 만족하는 실제 호출 성공을 보장하지 않았다. 보호 조건은 완화하지 않았다. Azure 계획 재현 1회를 포함해 총 5회 시도했으며 섹션 작성까지 도달하지 못했다. 따라서 **캐시 적중률·비용 절감·완성 품질 비교 결과는 아직 없다**. 비용과 토큰은 공급자 미보고 `null`이다. 도구의 `spentEstUsd`는 오류 시 보수적으로 차감한 예산 예약액이며 실제 청구액이 아니다.

이 과정에서 실험 도구는 HTTP 200 내부 오류 봉투를 분류하도록 보완했다. 서버 런타임에는 적용하지 않았다. 이후 재실행 시 동일 조건에서 계획 호출이 가능한 공급자를 먼저 확인하고 전체 비교를 실행한다. 도구는 T5 사실 검증·독립 questions 경로·사람 평가는 포함하지 않으므로 조립 성공만으로 완성 노트 품질을 판정하지 않는다.

## 이 검토의 검증

- 실험 도구 추가 후 전체 게이트 재실행: 1,214 tests, 1,213 pass, 0 fail, 1 skip.
- `busy providers` 개별 재현: 1 pass, 0 fail. 과거 실패 기록은 재현되지 않음.
- HTTP 직렬화 누락과 중첩 cache_write_tokens 누락: 합성 값으로 재현.
- CWS `--dry-run --skip-tests` 재실행: 92개 엔트리 통과. 위 전체 테스트는 별도로 실행했다. 실제 ZIP 생성·업로드 및 인쇄 기하/실제 품질 검증과 구분.

## 공식 문서

- [OpenRouter prompt caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching): provider sticky routing, provider.order 우선, session_id 및 prompt_cache_key, usage 세부 필드.
- [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching): 정확한 접두부 재사용과 캐시 제어. 실제 선택 공급자의 지원과 ZDR 호환성은 호출 전 별도 확인.
