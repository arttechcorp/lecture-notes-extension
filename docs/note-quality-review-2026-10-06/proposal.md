# Summrizei 노트 품질 개선안

2026-10-06 · 상태: 검토 제안. 런타임 코드·DB·배포 변경 없음.

추천은 **내용 보존을 먼저 평가하고, 의미 중심 초안을 만든 뒤, 검증된 내용을 기존 디자인 에셋으로 조판하는 구조**다. 계획 세션이 작성 워커를 위임하는 방식은 유용하지만, 모델 대화에 전체 실행 상태를 맡기기보다 현재 코드 오케스트레이터가 예산·재시도·체크포인트를 소유하게 한다. Jev는 삭제 결정자가 아니라 근거 검토 대상을 찾는 보조 판정기로 재배치한다.

## 1. 실제 관측: Jev가 원문을 과도하게 잘라내는가

[실측 화면](index.html)과 [수치 JSON](measurements.json)은 로컬 진단 파일의 허용된 수치만 추출했다. 원문·계정·강의 식별자는 포함하지 않았다.

| 기록 | 클라이언트 버전 | 초안 판정 주장 | 낮은 점수 | 비율 | Jev 블록 보류 | 개별 주장 제거 | 최종 탈락 블록 |
|---|---|---:|---:|---:|---:|---:|---:|
| A | 2.2.0.3 | 154 | 9 | 5.8% | 3 | 3 | 5 |
| B | 2.2.0.5 | 207 | 22 | 10.6% | 5 | 10 | 8 |
| C | 2.2.0.5 | 124 | 13 | 10.5% | 5 | 7 | 8 |
| D | 2.3.0.2 | 165 | 11 | 6.7% | 4 | 1 | 5 |

- 진단 5개 중 SUPPORT_SCORES 집계가 있는 4개. 세 강의 패키지이며 A/C는 같은 강의의 다른 시점 기록이다. 독립 표본도, 버전별 비교 실험도 아니다. 나머지 1건은 데이터 없음이지 삭제 0건이 아니다.
- 최신 D에서는 T5 복구 시도 4블록 중 2블록을 승인했다. 낮은 주장 11개와 복구 2블록은 단위가 달라 빼면 안 된다. 과거 기록의 T5_REPAIR 부재도 0회로 해석하지 않는다.
- `low`는 **최초 초안 검증의 낮은 점수**, `trimmed`는 블록을 살리면서 제거한 주장, `blocks`는 T5가 통째로 보류한 블록이다. 최종 탈락 블록에는 Jev 보류가 포함된다. 이 수치를 더하지 않는다.
- 현재 집계는 원문 삭제율, 옳은 주장 오판율, 블록 안 정상 설명의 동반 손실량을 알려주지 않는다. 원문과 최종 노트의 글자 수 비율도 학습 내용 보존율이 아니다.

### 현재 코드에서 확인한 원인

1. `lib/stages.js:237`에서 현재 전처리 판정은 T2 중요도만 실행한다. T1 발화 분류·T3 boilerplate·T4 figure API가 존재한다는 사실을 실제 노트 경로에서 실행된다는 증거로 쓰면 안 된다. 중요도는 유닛에 붙어 계획으로 전달되며 이 단계가 직접 원문 유닛을 삭제하지 않는다.
2. `lib/verify.js:133`의 T5 기준은 기본 0.5다. 주장에 **인용된 근거만** 합쳐 판정한다. 근거 ID 누락이나 인접 발화 부족을 잘못된 주장과 구별할 수 없다. 8,000자를 넘는 주장/근거는 자르지 않고 미판정 처리한다.
3. `lib/stages.js:446` 이후에는 낮은 주장을 복구하거나 제거한다. nullable 칸/목록 항목이면 부분 제거하지만 필수 칸이거나 제거 후 계약이 깨지면 블록 전체를 보류한다. 이때 정상 주장도 함께 빠질 수 있다.
4. 형식·의미 검증 복구와 T5 복구가 블록별 예산을 공유한다. 형식 복구를 이미 사용한 블록은 T5에서 새 복구 기회를 받지 못한다. 네트워크 재시도와 대체 모델 호출은 별도라서 이를 ‘API 호출이 무조건 한 번’이라고 표현하면 부정확하다.
5. `lib/note-contract.js:1204` 이후에는 사라진 블록을 참조하는 문항·지도·계산 등이 추가 정리된다. 최종 블록 건수만으로 직접 삭제와 연쇄 손실을 구분할 수 없다.
6. T5 이전에도 Writer의 null, 스키마 salvage, 숫자·참조 오류가 내용을 줄인다. `lib/preprocess.js`의 반복 정리·필터, 계획 정규화의 상한, `lib/stages.js:73`의 전역 입력 축약도 별도로 추적해야 한다. Jev 하나를 원인으로 단정하지 않는다.

**판단:** 과잉 삭제 위험이 있는 구현 경로와 실제 블록 보류는 확인됐다. 오판에 의한 과잉 삭제 규모는 아직 미측정이다. 기준을 무작정 낮추거나 Jev를 제거하기 전에 아래 비교 측정이 필요하다.

## 2. 아키텍처 선택

| 대안 | 변경 | 장점 | 부담 | 판단 |
|---|---|---|---|---|
| A. 현재 구조 보강 | 근거 확장, 부분 복구, 계측, 크기 분할 | 빠르게 현상 개선·기준선 확보 | 생성 모델이 복잡한 지면 계약까지 담당 | 첫 단계로 적용 |
| B. 의미 초안 → 검증 → 블록 조립 | 내용 계약을 지면 계약과 분리 | 내용 보존과 디자인을 독립 개선, 실패 범위 축소 | 중간 계약·컴파일러와 이행 필요 | 추천 목표 |
| C. 자유 대화형 멀티에이전트 | Planner가 임의 도구·워커를 반복 호출 | 비정형 예외 처리의 유연성 | 비용·종료 조건·개인정보·재현성 복잡 | 현재 기본 경로로 채택하지 않음 |

B가 반드시 호출 수를 늘린다는 뜻은 아니다. 현재 섹션 Writer를 의미 초안 Writer로 대체하고 조립은 코드로 처리한다. 기존 B01–B18 에셋, 렌더러, 암호화 저장과 상태 머신을 재사용한다. 의미 초안만으로 개념 설명 품질이 자동 향상된다는 보장은 없으므로 A/B 품질 평가로 결정한다.

## 3. 추천 생성 흐름과 계약

`인식 → 근거 목록/학습 항목 → Plan → 섹션 초안 병렬 작성 → 근거 복구·검증 → 연결 편집/문항 → 블록 조립 → 조판 검수`

### 근거와 학습 항목

- 원천 ID·발화/슬라이드 위치·수식/도표 참조를 보존한다. 원자료는 허용된 암호화 파생 데이터로만 남긴다.
- `learningItem`은 정의, 인과, 절차, 비교 기준, 사례, 조건, 예외, 수식, 해석 주의 중 하나이며 `evidenceIds`, 중요도, 정정 관계를 가진다.
- 중요도 낮음은 삭제 명령이 아니다. 각 항목의 처리 상태를 `included / merged / deferred / excluded`로 기록한다. 제외 사유는 중복·비수업 내용·인식 불가 등 제한된 코드다.
- 핵심 항목뿐 아니라 예외·조건·대표 사례의 포함 상태를 따로 본다. 모델이 만든 항목 목록 자체가 누락됐을 수 있으므로 표본 사람 검수로 보정한다.

### Plan

필드: `sectionId`, 학습 질문, `learningItemIds`, 원천 유닛/교차 유닛, 핵심 개념, 선수 개념, 비교 축, 설명해야 할 조건·예외, 그림/수식 필요성, 예상 출력량, 워커 유형.

계획이 제공하는 것은 ‘이번 단원에서 무엇을 이해해야 하는가’다. 페이지 수와 빈칸 수를 먼저 고정하지 않는다. 모든 항목에 배정/병합/보류/제외 상태가 있어야 하며, 미배정 핵심 항목은 계획 수정 대상으로 돌린다.

### SectionDraft

- `claimId`: 호스트가 부여한 불투명 ID. 문장 해시를 서버 식별자로 보내지 않는다.
- `role`: definition / intuition / mechanism / condition / exception / example / comparison / argument 등.
- `text`, `basis`, `evidenceIds`, `conceptIds`, `dependsOn`, `verificationState`.
- 관계·비교·계산은 typed 객체를 유지한다. 자유 산문 덩어리를 만든 뒤 또 LLM으로 구조화하는 이중 생성은 피한다.
- 지면의 색·패딩·번호·HTML은 출력하지 않는다. 형식상 필수인 빈 슬롯을 메우려는 중복 설명도 만들지 않는다.
- 개념은 정의 → 이해를 돕는 설명 → 성립 원리 → 조건/예외 → 적용 순서로 설명하되, 원리에 해당하지 않는 역사·철학 강의에 mechanism을 강요하지 않는다. 논증형은 주장–근거–숨은 전제–반론–한계, 경영형은 정의–작동–가정–비교–사례·의사결정 구조를 사용한다.
- 출처에 없는 교육적 비유는 허용 옵션과 별도 basis가 있어야 한다. 검증에서 빠져나오려고 lecture를 external로 바꾸지 않는다.

### 제한된 워커와 세션

- **Planner:** 범위와 설명 목표를 설계. 모델은 도구/워커 요청을 구조화해서 제안할 수 있다.
- **섹션 작성 워커:** 자신의 근거 묶음, 공통 용어 정의, 이웃 단원 요약 계약만 받는다. 독립 섹션은 병렬, 선수 관계가 중요한 섹션은 검증된 선행 요약을 받은 뒤 실행한다.
- **조건부 전문 워커:** 수식·단위/계산, 비교·논증, 도표 해석, 근거 복구. 해당 항목이 있을 때만 호출한다. 단순 산술은 코드가 맡는다.
- **연결 편집 워커:** 검증된 섹션의 핵심 명제·조건·연결 관계로 용어 일관성, 모순, 중복을 확인한다. 기존 본문 전체를 재작성하지 않고 변경 제안 목록을 반환한다. 수정된 주장만 다시 검증한다.
- **문항 작성:** 본문 확정 이후에 시작한다. 살아남은 본문만으로 답할 수 있고 해설이 그 근거를 가리켜야 한다.
- 실행 상태는 코드가 소유한다. `job → stage → task → attempt`를 구분하고 단계 입출력·의존성·정책 버전을 암호화 체크포인트로 저장한다. 공급자 session_id는 대화 기록이나 재개 보장으로 해석하지 않는다.
- 같은 작업 재개는 성공 결과를 재사용한다. ‘새로 만들기’는 명시적인 generation revision을 바꾼다. 모델 변경·동의 변경·입력 변경도 구별한다. 서버는 본문을 보관하지 않으므로 불명확한 전송 실패를 서버 대화 복구 기능으로 해결할 수 없다.
- 초기 동시성 후보는 작성 2/4/8을 비교한다. 출력량 사전 예측으로 작은 단위로 나누고, 429/timeout 시 동시성을 줄인다. 정확한 비용·지연 상한은 측정 후 결정한다.

## 4. Jev를 보존 중심으로 재설계

### 판정과 조치를 분리

| 상태 | 조치 |
|---|---|
| 근거 충분 | 내용 유지 |
| 인용 근거 부족 | 인접 발화·같은 슬라이드·정정 후 발화·허용 교차 유닛을 제한된 범위로 검색 |
| 확장 근거로 지지됨 | 올바른 evidenceIds를 붙이고 재검증 |
| 해석/복합 주장이라 판단 어려움 | 원자 주장 분리 또는 상위 검토 워커로 전달 |
| 실제 모순 확인 | 정정 근거로 해당 주장만 수정 |
| 끝내 불명확 | 확정 본문과 분리한 ‘확인 필요’ 상태로 암호화 보존. 학생에게 사실로 제시하지 않음 |
| 판정 누락/실패 | unjudged로 표시. 통과나 거짓으로 바꾸지 않음 |

- 첫 Jev 점수는 검토 우선순위로 사용한다. 낮은 점수만으로 되돌릴 수 없는 삭제를 하지 않는다.
- 근거 확장은 전체 강의를 매번 붙이는 방식이 아니다. 관련 근거를 먼저 찾고 허용량 초과면 근거 묶음을 분리한다. 여러 묶음 중 점수 최댓값만 취해 통과시키지 않으며 모순 근거도 함께 확인한다.
- 형식 복구와 사실 복구 예산을 분리한다. 초기 후보는 안전한 코드 정규화 → 근거 재연결 1회 → 문장 수정 1회 → 고위험만 상위 검토 1회다. 전역 작업 예산을 넘으면 보류한다. 횟수는 측정 전 제안값이다.
- 필수 정의가 불확실해도 정상인 조건·사례를 저장 구조에서 파괴하지 않는다. 다만 그 정의에 의존하는 설명·문항은 안전한 본문으로 승격하지 않는다. **보존과 확정 표시를 별개로 한다.**
- Jev가 high score인 주장을 ‘사람이 확인한 정답’으로 취급하지 않는다. 숫자·단위·수식 의미와 도메인 오류는 별도 검증이 필요하다.

### 실제로 보고 판단할 비교 화면

개발 전용 화면에 네 칸: `근거 → 검증 전 초안 → 점수/복구/이유 → 최종 노트`.

선택한 주장과 관련한 근거만 메모리에서 표시한다. 상태는 유지 / 수정 / 직접 보류 / 블록 동반 손실 / 의존 연쇄 보류 / 미판정. ‘왜 사라졌는가’에서 root cause와 후속 결과를 연결한다. 서버로 본문·내용 해시·근거 문자열을 보내지 않는다.

지표는 다음처럼 정의한다.

- `judge_low_rate = 초기 low / 초기 judged` — 현재 계산 가능.
- `collateral_loss_rate = 직접 저점수 때문이 아닌 블록/참조 보류 주장 / 검증 전 초안 주장` — 추가 기록 필요. 같은 claimId는 한 번만 센다.
- `false_withhold_rate = 사람이 supported로 판정한 주장 중 시스템이 보류한 수 / 사람이 supported로 판정한 수`.
- `false_accept_rate = 사람이 unsupported로 판정한 주장 중 확정 본문에 남긴 수 / 사람이 unsupported로 판정한 수`.
- `required_item_coverage = 최종 노트에 정확히 표현된 필수 학습 항목 / 사람이 정한 필수 학습 항목`.
- 복구 성공률은 시도/수락/예산 때문에 건너뜀/미판정/네트워크 실패로 나누고, 주장·블록 단위를 섞지 않는다.

과거 최종 노트만으로 삭제 전 초안을 복원했다고 주장하지 않는다. 기존 암호화 단계 캐시가 남아 있다면 로컬에서 읽어 비교하고, 없으면 계측을 추가한 새 실행이 필요하다. 현재 HTML은 집계 뷰이며 이 네 칸 비교 기능은 아직 구현되지 않았다.

### 평가 설계

1. 한국어 인문 논증, 경영 비교·사례, 경제·회계 수식, 영어 자료+한국어 발화, 인식 누락 조건을 포함한 동의된 평가 강의를 선정한다.
2. 첫 탐색 표본은 강의당 40개, 6강의 총 240개 주장쌍을 제안한다. 낮음/경계/높음/미판정과 정의·조건·예외·사례를 층화한다. 이 표본 크기는 확정 정확도 보증이 아니다.
3. 두 사람이 점수를 보지 않고 supported / contradicted / insufficient-evidence / ambiguous를 표시하고 불일치를 조정한다. 동일 강의의 문장이 튜닝·평가 양쪽에 섞이지 않도록 강의 단위로 분리한다.
4. 현재 0.5 삭제 경로 / 삭제 없는 shadow / 근거 확장+선별 복구 경로를 같은 입력으로 비교한다. shadow 결과는 학생용 확정 본문에 자동 반영하지 않는다.
5. 임계값만 바꾼 재계산은 복구 모델의 실제 응답을 시뮬레이션하지 못한다. 실제 복구 효과는 별도 호출 실험으로 측정한다.
6. 전체 정확도·ECE뿐 아니라 false withhold/accept, 필수 항목 보존, 사람이 평가한 설명·구조, 총 비용·p50/p95 지연을 함께 본다. API 미응답을 제외한 정확도와 전체 요청 성공률을 별도 보고한다.

## 5. 수식·도표·이미지

- 수식은 등록부 참조를 유지하고 KaTeX 파싱, 원본 기호/분모/첨자 비교, 단위·계산 검산을 구별한다. KaTeX 성공이 수학적 정확성은 아니다.
- 그래프는 관측 데이터가 있으면 축·단위·범례·표본 범위를 명시한 결정론적 SVG/표로 그린다. 근거 없는 숫자로 보기 좋은 그래프를 만들지 않는다.
- 원자료에 도표가 있고 인식이 충분하면 검증된 재조판, 불충분하지만 적법한 영역 크롭이 있으면 크롭+근거 기반 설명, 둘 다 없으면 누락 상태를 표시한다.
- 개념도는 검증된 관계 객체로 그린다. 단순 시간 순서를 인과 화살표로 바꾸지 않는다.
- 텍스트 없는 도식을 무조건 버리지 않도록 `figureId ↔ 시간대/유닛 ↔ 설명 근거` 연결을 강화한다. 모든 그림에 억지 OCR 문장을 만들지는 않는다.
- crop 존재/선택/품질 거절/계획 배정/본문 참조/렌더 성공을 각각 기록해, ‘이미지가 없다’가 어느 단계 문제인지 보이게 한다.

## 6. 사용자가 제공한 Gemini PDF 제작 설명에서 반영할 것

제공 문장은 제작자가 설명한 작업 방식으로 취급한다. 실제 비공개 시스템 프롬프트나 성능 증거라고 단정하지 않는다.

| 요소 | 반영 방안 | 주의점 |
|---|---|---|
| 타이포그래피와 시각 계층 | `landing/design.md` 기준 토큰과 기존 NoteSpec 에셋을 공유. 제목·정의·예외·자료·문항 위계를 명시 | 임의 Tailwind 팔레트/그라데이션을 늘리는 것보다 기존 브랜드·인쇄 가독성 우선 |

현재 이미 있는 부분: `lib/note-spec.js`에 A4 print CSS, 부분 break-inside, 표 머리 반복 등이 있다. `sandbox.html:99`와 `landing/library.js:332`의 기존 인쇄 경로도 폰트·이미지 완료 대기를 사용한다. 다만 이미지 decode 실패를 catch로 흡수하므로 준비 대기와 실패 검출은 별개다. 새로 필요한 핵심은 렌더 결과를 품질 기준과 대조하고 제한된 재배치를 하는 검수 루프다.

### 조판 피드백 루프 계약

- 입력: 검증 완료 Note + designVersion + rendererVersion. 내용 생성 단계로 되돌아가 페이지를 맞추기 위해 문장을 줄이지 않는다.
- 측정: 가로/세로 overflow, 수식 렌더 오류, 미완료 이미지, 제목만 남은 페이지, 정답 첫 줄 분리, 표 행 잘림, 본문 최소 글자 크기, 글자·도형을 함께 고려한 점유율.
- 교정 순서: 불필요한 빈칸 제거 → 의미 단위 재배치 → 표/긴 설명을 허용 지점에서 분할 → 패딩·행간을 디자인 허용 범위 내 조정 → 페이지 추가.
- 제목+첫 문단, 식+변수 설명, 질문+최소 답안 단서 등 ‘함께 있을 최소 묶음’을 정의한다. 긴 블록 전체 고정은 금지한다.
- 제한: 자동 재조판 최대 2회라는 초기 후보를 평가한다. 그래도 실패하면 명시적인 인쇄 경고와 안전한 기본 배치를 제공한다. 재시도 상한은 제품 측정 후 확정한다.
- 개발 CI는 합성 노트를 Headless Chromium으로 인쇄하고 PyMuPDF 등으로 페이지 bbox·텍스트·이미지 위치를 검사하며 렌더 이미지도 확인한다. 글자 수만으로 통과시키지 않는다.
- 제품은 브라우저 메모리에서 DOM 기하와 준비 상태를 검수하고 사용자가 요청한 노트 PDF를 로컬로 출력한다. 사용자 본문을 서버 Headless Chrome/PyMuPDF로 보내는 구조는 제안하지 않는다. 개발용 Node/Python 도구를 확장 런타임에 넣지도 않는다.

## 7. 서버 캐시 기록 설계

사용자가 서버 기록에 동의한 범위는 캐시와 실행의 콘텐츠 없는 메타데이터로 반영한다. 원문/노트 저장 정책을 넓히지 않는다.

### 구분할 세 종류

1. **로컬 결과 캐시:** 암호화된 완료 단계 결과. hit면 해당 모델 호출 없음.
2. **공급자 prompt 캐시:** 동일 접두부 처리 절약. 요청·생성은 여전히 발생.
3. **응답 전체 캐시:** 입력에 대응하는 본문 결과 저장. 현재 제안의 대상이 아니며 공급자 ZDR와 별도 확인이 필요.

`server/index.js:626`은 현재 prompt/completion token을 남기고 공급자의 cache 상세를 버린다. `usage_events`에는 캐시 적중 관련 열이 없다. 서버 promptVersion은 응답에 있지만 `lib/stages.js:162,169`의 캐시 키는 stages VERSION을 사용한다. 서버 프롬프트만 바뀌었을 때 이전 결과를 재사용할 위험을 먼저 고쳐야 한다.

### 저장 계약

| 필드 | 뜻 |
|---|---|
| logical_task_id / attempt_id | 논리 작업과 실제 공급자 호출을 분리한 불투명 ID |
| cache_kind / cache_status | local_result / provider_prompt, hit / miss / unknown / not_applicable |
| cached_input_tokens | 공급자가 보고한 재사용 입력. 미보고 null, 확인된 0과 구분 |
| cache_write_tokens | 공급자가 보고한 캐시 생성 입력. 의미는 provider adapter에서 정규화 |
| provider_reported_cost / cost_status | 실제 보고·사후 조회·추정 예약을 구별 |
| prompt_version / schema_version / policy_version | 생성·검증 계약 버전 |
| renderer_version / design_version | 로컬 렌더 캐시 무효화용 버전 |
| input/output tokens, latency, status | 기존 필드 재사용 |

- HTTP 내부 재시도까지 실제 호출별 attempt를 기록하고 요청 합계와 중복 집계하지 않는다. 상태 수정/중복 업로드는 멱등 처리한다.
- 로컬 cache hit는 공급자 호출이 없어 서버 원장만으로 관측되지 않는다. 별도 인증된 콘텐츠 없는 run 집계로 받는다. 클라이언트 보고값은 청구 정산의 신뢰 원천으로 쓰지 않는다.
- 모든 값은 허용 enum·범위 검사. 자유 텍스트 오류, 프롬프트, 본문 해시, 공급자 원본 응답 저장 금지. 접근·보관·계정 삭제 정책을 기존 원장 규칙과 맞춘다.
- token cache hit ratio는 `Σcached_input_tokens / Σinput_tokens`로 계산하되 보고 가능한 호출만 포함하고 미보고 비율을 같이 표시한다. 호출 hit 비율과 토큰 hit 비율을 섞지 않는다. ‘hit니까 X% 절감’으로 추정하지 말고 실제 cost를 비교한다.
- 안정된 지시/스키마/정책 접두부를 앞에, 섹션별 자료를 뒤에 둔다. 캐시를 위해 전체 강의 원문을 모든 요청에 반복하지 않는다.
- 프롬프트 캐시 지원·최소 토큰·TTL은 모델과 공급자별로 측정한다. 고정 공급자 경로의 안정성과 cache hit를 함께 평가한다. 가격표의 캐시 가격만으로 적중을 보장하지 않는다.

## 8. 실행 순서와 승인 기준

| 순서 | 작업 | 산출물/완료 기준 |
|---|---|---|
| P0 | 삭제 원인·cache 계측, 버전 키와 새로 만들기 의미 정리 | 불명확한 0 없음, 재개/새 생성 구분, 로컬 비교 화면 |
| P1 | 근거 확장, 원자 주장, 부분 복구, 보류 보존 | 사람 라벨 기준 잘못된 보류 감소, unsupported 확정 증가 여부 확인 |
| P2 | 의미 초안·블록 컴파일러, 커버리지 원장, 전문 워커 | 기존 경로와 동일 강의 A/B; 필수 항목·설명 구조 향상 검증 |
| P3 | 수식/도표 경로와 조판 검사 | 수식/이미지/참조·인쇄 잘림 회귀 통과, 실제 강의 검수 |

기존 정답/수치/참조 검증을 제거해서 생존율만 높이지 않는다. 최소 출시 조건은 합성 fixture의 깨진 참조·파싱 불가 수식·가로 overflow 0, 실제 평가셋의 중대한 사실 오류 수동 확인, 필수 학습 항목 누락과 false withhold/accept를 공개 가능한 수치로 보고하는 것이다. 학습 품질·비용 목표의 수치 자체는 기준선을 측정한 뒤 고정한다.

저장 포맷을 바꾸면 AGENTS 버전 규칙에 따라 major와 이전 파일 읽기/이행이 필요하다. 기존 파일을 일괄 삭제하거나 AI로 강제 재생성하지 않는다. 형식 변화가 없는 출력 개선은 minor 대상이다. 배포되지 않았더라도 실제 사용자 보관함 파일이 있으므로 호환성을 검토한다.

## 9. 연구·검토 근거와 한계

- [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents): 코드로 정한 workflow와 모델이 경로를 결정하는 agent 구분, orchestrator-workers/evaluator-optimizer 패턴. 우리 설계 선택은 이 문서를 적용한 판단이며 효과 실측은 아니다.
- [TypeSafe Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13): 2026-10-02 검토 표시. 복합 추론·숫자·무관한 긴 문맥·choice 순서·적대적 자료의 한계를 안내한다. 따라서 T5의 한국어 대학 강의 오류율을 별도 측정해야 한다. score primitive의 수치 보간 한계를 noul 지원 확률 전체의 무효화로 일반화하지 않는다.
- [OpenRouter prompt caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching): 캐시 토큰 보고와 공급자별 경로/캐시 차이를 확인한 기존 조사에 근거한다. 실제 서비스 hit rate는 아직 없다.
- [OpenRouter response caching](https://openrouter.ai/docs/guides/features/response-caching): prompt caching과 다른 저장 기능. 현재 제안에서는 활성화하지 않는다.
- [KaTeX options](https://katex.org/docs/options.html): 기본 출력은 HTML+MathML이다. auto-render를 쓰는 것과 모든 식을 SVG로 만드는 것은 같은 뜻이 아니다.
