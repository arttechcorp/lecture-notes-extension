# 운영 런북 (Operational Runbook)

문서 최종 수정: 2026-10-02. 서버 코드가 변경되면 이 문서를 반드시 갱신하세요.

---

## 1. 공급자 장애 (Provider Outage)

**증상**
- 특정 기능(비전, STT, 판정)이 작동하지 않으며 사용자가 오류를 보고합니다.

**확인**
- 공급자 상태 페이지 확인 (OpenRouter, Groq 등)
- 서버 로그에서 `provider_failed`, `provider_busy`, HTTP 5xx 확인
- `/v1/me` 응답의 `features` 필드 확인

**조치**
1. `FEATURE_FLAGS_JSON`에서 해당 기능을 `false`로 설정합니다.
   - 예: `{"vision":false,"stt":true,"background":true,"judge":true}`
2. 서버를 재배포합니다 (환경 변수 갱신).
3. 사용자에게 공지합니다 (메일, 문서, 내부 채널).

**복구 확인**
- `/v1/me`에서 `features`에서 해당 기능이 제거되었는지 확인
- 새 요청이 `feature_not_in_account_plan` 거부를 받는지 확인

**주의**
- 플래그를 끄는 것만으로는 실행 중인 작업을 중단하지 않습니다.
- 긴급 상황이면 이전 컨테이너 리비전으로 롤백을 고려하세요.

---

## 2. 키 회전 (Key Rotation)

**증상**
- API 키 유출, 정기 보안 점검, 공급자 지원 중단 등의 사유.

**확인**
- 시크릿 관리자에서 현재 키와 만료일 확인
- 새 키가 같은 공급자(OpenRouter, Groq)에서 발급되었는지 확인

**조치**
1. 시크릿 관리자에서 새 키로 교체합니다.
   - `OPENROUTER_API_KEY`
   - `GROQ_API_KEY` (STT 사용 시)
2. 서버를 재배포합니다.
3. 구 키를 해당 공급자 콘솔에서 비활성화합니다.
4. 몇 분 후 새 요청이 성공하는지 확인합니다.

**복구 확인**
- `/v1/vision` 또는 `/v1/stt` 테스트 요청이 200을 받는지 확인
- 구 키는 거부되는지 확인

**주의**
- 키 교체 중에도 실행 중인 작업은 기존 키를 사용합니다.
- 인스턴스가 여러 개면 모두 동시에 갱신해야 합니다.

## 3. 원가 급증 (Cost Spike)

**증상**
- 사용량 상태 파일(`USAGE_STATE_FILE`, 기본 `usage.json`)의 계정별 `spentCents`가 급증했습니다.
- 공급자 콘솔에 비정상 요청이 보입니다.

**확인**
- 사용량 상태 파일에서 계정별 `requests`·`spentCents` 확인 (Supabase `usage_events` 집계는 미구현 — architecture-v2 §12 계획)
- 특정 계정(account)이 비정상 사용했는지 확인
- 공급자 콘솔에서 요청 수와 토큰 사용 대조

**조치**
1. `GLOBAL_COST_CENTS` 환경 변수를 낮춥니다.
   - 예: 기본값 15000 센트($150) → 5000 센트($50)로 조정
2. 필요하면 `MAX_COST_CENTS` (계정당 월 한도)도 낮춥니다.
3. 서버를 재배포합니다.
4. 비정상 계정을 조사하고, 필요하면 `ACCOUNT_LIMITS_JSON`에서 한도를 개별 설정합니다.
5. 공급자 콘솔의 지출 상한도 설정합니다.

**복구 확인**
- 새 요청이 `quota_exceeded` 거부를 받는지 확인
- Supabase에서 일일 비용이 안정화되는지 모니터링합니다.

**주의**
- 전역 한도에 도달하면 모든 사용자의 요청이 차단됩니다.
- 한도를 정상화하려면 원인을 먼저 파악한 뒤 환경 변수를 갱신하고 재배포하세요.

## 4. 진단 파일 처리 (Diagnostic File Handling)

**증상**
- 사용자가 문제 보고 시 진단 파일(`summrizei-diagnostic-<날짜>.json`)을 첨부했습니다.

**확인**
- 평문 JSON이다: `{v: 2, createdAt, version, events: [...]}`. `version`은 확장 버전이다.

**조치**
1. 파일을 열어 `events`의 `stage`·`status`·`code`·`ms`로 실패 지점을 찾습니다. 강의 내용은 들어 있지 않습니다(허용 필드만 내보낸다).


3. 분석 후 원본 파일을 삭제합니다 (지원 메일 대화에서).

**복구 확인**
- 복호화 성공 여부 확인
- 민감한 데이터가 노출되지 않았는지 확인

**주의**
- 개인키는 오프라인 환경에서만 보관하세요.
- 도구 자체는 개인키를 stdout에 출력하지 않습니다.
- 파일에서 강의 내용은 없습니다 (기술적으로 저장되지 않음).

## 5. 사이트 호환성 이슈 (Site Compatibility Issue)

**증상**
- 특정 LMS(LearnUs, Moodle 등) 또는 사이트에서 백그라운드 처리가 실패합니다.
- 사용자가 "백그라운드를 지원하지 않는다"는 오류를 보고합니다.

**확인**
- 사용량 이벤트의 `host` 필터는 미구현 — architecture-v2 §12 계획
- 오류 코드: `SRC_AUTH_EXPIRED`(인증 만료, `lib/media-source.js`). `SRC_PROTECTED`(보호조치 감지)는 §8 계획 코드다

**조치**
- **미구현** — architecture-v2 §6.1 계획에서 사이트별 백그라운드 끄기 기능은 아직 구현되지 않았습니다.
- 현재 대안: 사용자에게 실시간 모드(탭 열린 채) 사용을 안내합니다.
- 우회책: 특정 호스트에서만 실시간 모드를 기본값으로 하는 클라이언트 설정을 검토할 수 있습니다.

**복구 확인**
- 해당 사이트 사용자들이 실시간 모드로 전환했는지 모니터링

**주의**
- 개발 로드맵에서 지원할 예정입니다.

## 6. 롤백 순서 (Rollback Sequence)

**증상**
- 새로운 배포가 심각한 오류를 유발했습니다.

**순서** (가장 빠른 것부터)
1. **서버 기능 플래그** (즉시, 재배포 없음)
   - `FEATURE_FLAGS_JSON`에서 기능을 끕니다.
   - 예: `{"vision":false}` — 비전 기능 비활성화.

2. **이전 컨테이너 리비전** (분 단위)
   - 클라우드 호스팅(Cloud Run, Fly.io 등)에서 이전 리비전으로 전환합니다.
   - 모든 환경 변수는 유지됩니다.

3. **이전 확장 버전** (시간 단위, 웹스토어)
   - 웹스토어에서 이전 버전을 재게시합니다.
   - 사용자는 수동으로 다시 설치하거나 자동 업데이트를 대기합니다.

**복구 확인**
- 각 단계마다 테스트 요청을 보내 정상 작동 확인
- 사용자 보고 모니터링

**주의**
- 플래그 끄기는 즉시 적용되지만, 확장 배포는 느립니다.
- 컨테이너 리비전 롤백은 대부분의 시나리오에서 충분합니다.
- 플래그를 다시 키려면 서버를 다시 배포해야 합니다.
