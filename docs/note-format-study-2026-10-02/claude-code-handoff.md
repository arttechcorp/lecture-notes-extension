# Claude Code 전달 메모: 노트 양식 v3 × 파이프라인 v2

2026-10-02 · 확인한 체크아웃: `w/dev`, HEAD `bc85a8b`. 이 문서는 현재 산출물의 적용 경계와 추가 구현 계약을 정리한 인계 자료다. 실행 가능한 Note JSON Schema나 제품 구현 완료 보고서가 아니다. 기존 작업 변경과 지침 파일은 그대로 보존한다.

## 1. 판단

**디자인과 학습 구조는 전달할 수 있다. 하지만 디자인 파일만으로 Phase 6·7을 시작하면 중요한 데이터 계약을 구현자가 추측하게 된다.** `architecture-v2.md` §5.4는 Note를 노트 기획 세션의 산출물로 비워 두었고, §15는 Phase 6·7이 이 산출물에 의존한다고 명시한다. 현재 `proposal.md` §11에는 개념적 계약과 B06 예시가 있으며, 실행 스키마는 아직 별도로 정의해야 한다고 적혀 있다.

추가할 핵심은 **“이 내용 구조를 어떤 JSON으로 받고, 어떻게 근거를 검증하고, 어떤 순서로 안전하게 표시할 것인가”**다. 프롬프트 문장만 추가해서 해결할 수 있는 범위가 아니다.

## 4. 구현 전에 확정할 계약 8가지

### 4.1 NoteSpec → Plan → SectionDraft → Note의 실행 계약

공통 봉투와 각 B타입의 `content` 슬롯에 대해 타입, 필수 여부, null/빈 배열 의미, 문자열·배열 상한을 정한다. 허용 타입, 순서, 근거와 연결 ID를 서버와 클라이언트가 같은 계약으로 검증해야 한다.

권고하는 구분은 다음과 같다. 이름은 아직 실행 스키마가 아니며 기존 명명 규칙에 맞춰 고정한다.

- NoteSpec: 지원 B타입, 선택 조건, 타입별 슬롯, 편집 권장량, 전송 안전 상한, 제약 버전.
- Plan: 출력 섹션 ID, 원본 Unit 범위, 사용 가능한 근거 ID, 순서 있는 블록 계획, 전역 블록 계획, 수식·도표 참조.
- SectionDraft: Plan의 ID를 유지한 검증 전 블록 결과. 병렬 완료 순서가 문서 순서를 바꾸지 않음.
- Note: 문서 메타데이터, 정렬된 섹션·블록, 교차 참조, 답안 연결, 처리 상태·고지, 버전 정보. 바이트 크롭은 중복 삽입하지 않고 패키지 내 ID로 참조.

현재 검증기에 지원하지 않는 `oneOf` 등을 써 놓고 “JSON Schema 완료”로 판단하면 안 된다. 블록별 스키마 선택과 공통 봉투 검증을 분리하는 방식, 또는 최소한의 스키마 기능 확장 중 하나를 정하고 계약 테스트로 증명한다. 쓰지 않는 모든 B슬롯을 거대한 nullable 객체에 무작정 늘어놓는 우회도 피한다.

**화면의 슬롯 생략과 wire 데이터 생략은 별개다.** strict 객체에서는 필수 키를 유지한 채 null/빈 배열을 표현하고, 렌더러가 해당 내용과 여백을 생략할 수 있다. 의미 없는 빈 문자열로 미확인 값과 실제 빈 값을 섞지 않는다.

### 4.2 원본 Unit, 출력 단원, 근거 ID를 분리

현재 IR의 `unitId`는 슬라이드와 발화의 입력 단위다. 노트 기획안의 `unitId`는 출력 단원을 뜻한다. 같은 이름으로 그대로 합치지 않는다. 권고는 입력 `unitId` 유지, 출력은 `sectionId`, 포함된 입력은 `sourceUnitIds`로 구분하는 것이다.

근거는 별도의 인덱스 또는 대응 정보로 원래의 slide block / transcript segment / 위치 / 시간까지 돌아갈 수 있어야 한다. **문자열로 합친 IR만 받아서는 나중에 정확한 발화 ID를 복원할 수 없다.** 이 대응을 전처리에서 보존하거나 원 패키지 자료와 연결해 Writer 입력으로 제공한다. 필터·점진 슬라이드 병합 이후에도 원본 대응을 유지한다.

`evidenceRefs`와 `evidenceIds`를 혼용하지 않도록 canonical 이름과 필드 역할을 정한다. 권고는 내용 슬롯의 `evidenceIds[]`와 ID를 해석하는 별도 근거 인덱스다. 단원 밖 내용을 비교하려면 Planner가 허용한 교차 근거를 Writer 입력에 명시해야 한다. Global Writer도 검증된 자식 주장과 원 근거를 따라가며, 새 근거 ID를 만들지 않는다.

이미 정한 Point 내부 범위(`단원/사례/번호`)는 유지한다. 표시 번호는 “Point 1”이어도 내부 ID는 문서 전체에서 충돌하지 않아야 한다. 문항/답안, 정정 대상, 정의 참조도 같은 원칙을 따른다.

### 4.3 근거·수치 검증을 주장 종류별로 구분

v2 §6.5의 “출력 수치는 인용 근거에 있어야 한다”를 모든 출력에 같은 방식으로 적용하면 계산 결과와 학습 문항을 잘못 탈락시킨다. 다음을 분리해야 한다.

| 출력 종류 | 검증 대상 | 금지되는 우회 |
|---|---|---|
| 강의의 사실·수치 | 해당 주장/셀의 실제 근거, 단위, 부호, 조건 | 숫자가 강의 어딘가에 있다는 이유만으로 통과 |
| 계산 결과 | 근거 있는 입력값, 허용 연산, 단위, 정밀도·반올림, 코드 검산 | LLM이 `derived`라고 썼다는 이유만으로 통과 |
| 교육용 오답 문장 | 문항 유형, 정답, 원 개념에 근거한 수정 문장과 이유 | 거짓 문장을 사실 요약의 `supported`로 표시 |
| 허용된 가상 사례 | 해당 옵션 허용 여부, 가상 라벨, 적용 개념, 내부 수치 일관성 | 가상 수치가 실제 강의 사례나 통계로 승격 |
| 번호·날짜·처리 정보 | 코드가 생성한 구조 번호 또는 확인된 메타데이터·시스템 기록 | 모든 숫자를 강의 수치로 검사하거나 강의일 추정 |

예: 근거가 판매가격 12,000원·변동비 7,000원·고정비 1,000,000원이라면, 5,000원과 200개는 근거에 그대로 없더라도 검산된 파생값일 수 있다. 반대로 허용하지 않은 가상 시나리오의 가격 11,000원을 강의 사실로 쓰면 안 된다.

계산 검산은 허용된 연산과 타입이 있는 피연산자로 수행한다. 모델이 제공한 표현식을 `eval`하거나 임의 코드를 실행하지 않는다.

블록의 `origin` 하나만으로 내부의 모든 문장을 예외 처리하지 않는다. 혼합된 사례·해설·오답·정정은 검증할 최소 슬롯별로 역할과 출처를 구분한다. 외부 보강·가상 예 생성은 기존 기획대로 기본 OFF다. 이를 켜는 것은 새로운 제품 정책 변경이다.

### 4.4 수식·표·그래프의 슬롯과 실패 표현

B10은 단순한 수식 문자열 상자가 아니다. 원본 수식 참조, 변수와 단위, 가정, 계산 과정, 파생값, 결과 해석, 도표와 설명을 담을 수 있어야 한다. 원본 수식은 레지스트리 참조로만 사용하고, 새 유도식은 `derived`로 분리한다.

추가로 고정할 항목:

- `formulaId`·`figureId`·`cropId`의 소유자와 해석 방법. ID를 외부 URL이나 원본 미디어 경로로 대체하지 않음.
- verified 수식 직접 렌더 / 미검증 수식 크롭 / 크롭도 없는 경우의 확인 필요 표시.
- KaTeX 통과는 문법 검증이며 새 유도식의 수학적 타당성·숫자 검산을 대신하지 않음.
- 표 재조판에 필요한 셀 신뢰도 기준, 구조 보존 검사, 실패 시 크롭. 현재 figure의 단일 conf를 셀별 검증이 끝난 값으로 오인하지 않음.
- 도표의 캡션, 대체 설명, 축·단위·읽는 법·해석·한계 중 실제 근거가 있는 슬롯만 작성.
- 도표의 섹션당 초기 상한과 초과 시 관련 내용 뒤로 나누는 규칙. 기존 문서에는 실행 가능한 수치 상한이 없으므로 임의의 제품 확정값으로 보고하지 않음.
- Free의 미탐지와 수식 미검증을 필요한 위치와 처리 고지에 표시. 이를 빌미로 클라우드에 자동 전환하지 않음.

### 4.5 Planner / Section / Global / 코드의 책임

| 책임 | 권고 |
|---|---|
| Planner | 내용 기준 섹션, B타입·순서·근거 허용 범위, 중복 개념의 기준 위치 결정 |
| Section Writer | 개념·비교·논증·사례·자료·계산·단원 연결 정리. 문항과 답안은 같은 계약 단위로 작성 |
| Global Writer | 검증된 섹션 결과의 핵심 요약·지도·전체 연결. 원본 근거와 검증된 자식 주장 참조 |
| 코드 | 메타데이터 출처, 안정 ID·표시 번호, 문서 순서, 입력 누락·탈락 고지, 답안 링크, 필기 여백, 에셋·색·페이지·텍스트 내보내기 |

B13은 단원 또는 전체 범위로 쓰일 수 있다. 전역이라는 이유로 새 사실을 더하지 않는다. B01 메타데이터, B16 빈 필기란, 시스템 B17 고지는 불필요한 모델 호출로 채우지 않는다. 교수 공지는 실제 발언을 가진 콘텐츠이며 코드가 사실을 만들어서는 안 된다.

편집 권장 글자 수와 전송/스키마 안전 상한을 구분한다. 권장량을 넘었다고 핵심 조건을 자르지 않는다. `finish_reason=length`는 섹션 분할, 검증 오류는 실패 블록 1회 재생성이라는 v2 책임을 유지하고 재시도가 중첩되지 않게 한다.

### 4.6 실패한 블록에 연결된 문항·요약까지 점검

부분 실패를 블록 삭제로 끝내지 않는다. 해당 개념을 인용하는 요약, 문제, 해설, 비교 셀의 참조가 남는지 검사한다. 살아남은 근거로 성립하는 것만 유지하고, 아니면 연결 단위도 제외/보류하고 범위를 고지한다. 끊어진 링크와 본문에 없는 내용의 문제를 남기지 않는다.

시스템 처리 상태(`partial`, 공백 시간, 인식 실패, 검증 탈락 등)와 콘텐츠 판단 상태(`uncertain`, `conflicting`, 명시적 정정 등)를 분리한다. 교수의 최종 정정은 이전 주장과 함께 합쳐 버리지 않고 정정 관계를 유지한다. 통계용 로그에는 원문·노트 문장·수식·주장 텍스트를 넣지 않는다.

### 4.7 버전·재생성·호환성을 구분

`schemaVersion`은 데이터 구조, `noteSpecVersion`은 생성·검증 계약, `promptVersion`은 프롬프트, `designVersion` 또는 동등한 값은 표시용 에셋을 가리키도록 역할을 정의한다. 각 이름은 제안이며 실제 버전 저장 위치·호환 표는 구현 계약에서 확정한다.

v2 §8의 현재 재생성 규칙은 템플릿 변경 시 E~H 재실행이다. **CSS·SVG만 바뀐 경우 기존 Note를 H에서 다시 렌더링하는 방식은 비용을 줄일 수 있는 추가 제안**이며, 승인된 기존 동작인 것처럼 바꾸지 않는다. 콘텐츠 규칙/스키마 변경과 시각 변경의 무효화 범위를 구분해 계약에 반영한다.

LLM의 temperature 0만으로 같은 결과를 보장하지 않는다. 같은 Plan/Note 입력에 대한 렌더 순서는 코드로 결정하고, 이전 결과의 재사용은 버전·입력 다이제스트로 판단한다. 패키지 마이그레이션에서 미지 필드를 보존하는 정책과, 모델 출력/렌더 입력에서 미지 필드를 신뢰하지 않는 검증 정책은 별개다.

### 4.8 실제 렌더러와 내보내기 계약

- HTML/CSS/SVG를 모델 출력에 포함하지 않는다. 정해진 템플릿의 안전한 텍스트 슬롯과 허용된 구조만 사용한다.
- PDF는 모델이 정한 쪽 수에 맞추지 않는다. 제목+본문, 정의+필수 조건, 짧은 자료/해설, 질문+필기 공간을 묶는다. 긴 표는 열 제목과 사례/Point 문맥을 반복한다.
- 웹 해설 기본 접힘, 일반 PDF 뒤쪽 답안, P06 같은 쪽 아래 해설의 점검용 예외, 시험 모드의 답안 분리 여부를 명확히 한다. 답안 표시 상태는 Note의 사실 내용을 바꾸지 않는다.
- `document.fonts.ready`와 필요한 수식·크롭 준비 완료 후 인쇄한다. 내용 잘림을 CSS `overflow:hidden`으로 감추지 않는다.
- 제품과 데모가 공유하는 `landing/product-panel.css`, 현재 Markdown/강조/인용/수식 결합을 확인한다. 복사·텍스트 내보내기는 Note JSON에서 파생하는 어댑터로 처리할 수 있으며, 이를 위해 v1 생성 경로를 병행 운영하지 않는다.
- 최신 PDF는 레이아웃 참고다. PDF를 파싱해서 제품의 콘텐츠 스키마로 쓰지 않는다. v3 HTML의 실제 브라우저·모바일 재검증은 아직 남아 있다.

## 5. Claude가 먼저 만들어야 할 검증 가능한 산출물

1. **계약 묶음:** NoteSpec·Plan·SectionDraft·Note와 B별 content 스키마, 지원 버전, 근거/ID/숫자/수식 정책.
2. **책임·매핑 표:** 입력 필드→Writer 슬롯→검증기→렌더 블록. 없는 입력의 null/생략/보류 동작.
3. **합성 fixture:** 입력 IR·레지스트리·근거 인덱스, 예상 Plan/Note, 필수 주장·예상 실패, 렌더 시안. 기존 `examples.json`보다 한 단계 더 구체적인 실행 자료.
4. **검수 결과:** 타입 검증만 아니라 의미 보존·참조·분할·출처 경계를 포함한 통과/실패 기록.

최소 fixture 범위:

| 사례 | 통과 기준 |
|---|---|
| 이론 비교 | 같은 행의 기준 일치, 정의 중복 억제, 모르는 칸 미창작 |
| 인문 자료/토론 | 저자·교수·학생·관점 구분, 논쟁적 OX 강제 없음 |
| 경영 계산 | 근거 입력과 코드 검산 파생값 구분, 단위·반올림·분모 0 처리 |
| 교육용 오답 | 틀린 문장은 문제로만 표시되고 근거 있는 수정·이유와 연결 |
| 후반 정정·충돌 | 오래된 수치의 무표시 잔존 없음, 확인 필요 범위 보존 |
| 긴 비교표·긴 사례 | 글자 축소·잘림 없이 넘김, 제목·열·Point 문맥 유지 |
| Writer 일부 실패 | 유지 가능한 부분 보존, 끊어진 답안·요약 참조 0 |
| 수식/크롭 실패와 Free | 미검증 LaTeX 무표시 노출·임의 그래프 복원·자동 클라우드 전환 0 |
| 입력 속 악성 지시 | 출력 규칙 변경·HTML 실행·외부 전송 지시 이행 없음 |
| 색·서체만 변경 | 정의한 버전/캐시 정책에 맞는 재생성 범위와 결과 확인 |

실제 강의 자료는 기존 동의·원본 미저장·파생물 암호화 규칙을 따른다. 저장소의 공개 fixture는 직접 작성한 합성 자료로 만든다. 골든셋을 위해 실제 전사·슬라이드·생성 노트를 평문 저장소에 추가하지 않는다.

## 7. 검토 범위

6.1 Sol은 백엔드 계약, 6 Luna는 내용·지면 전달 경계를 읽기 전용으로 검토했다. Antigravity와 Devin에는 실제 강의·원본 PDF·인증 자료 없이 검증 규칙과 구현 제약을 요약한 별도 브리프를 전달했다. 외부 검토 의견은 현재 코드·기획과 대조한 뒤 반영하며, 모델 수가 많다는 사실을 완전성의 증명으로 삼지 않는다.

외부 검토의 채택 여부:

| 검토 | 확인·반영 | 채택하지 않은 제안 |
|---|---|---|
| 6.1 Sol | Note/Plan 부재, 입력/출력 Unit 혼동, 파생값 검증, 버전·실패 계약 | 새 학습 정책을 사용자 승인 없이 확정하지 않음 |
| 6 Luna | B/P 구분, 입력→슬롯 매핑, 답 공개, 실행 fixture와 파일 우선순위 | 이미 문서에 있는 원칙을 신규 누락처럼 취급하지 않음 |
| agy / Gemini 3.8 Flash | 오답 문항·정정·셀별 근거·실패 종속성 | 일반 DAG 엔진이나 excluded_stub 상태를 필수 구현으로 강제하지 않음. 기존 참조와 고지로 요구를 만족할 수 있음 |
